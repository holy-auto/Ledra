## 1. Founder-Market Fit: なぜ堀越友輔がやるべきか

### 1-1. 「一次情報」という根本的優位

Ledra の対象市場は「コーティング/PPF 施工店」という、外から見えにくい専門業界。

堀越友輔は **自動車コーティング・PPF 施工店 `detailing_holy` のオーナー兼施工者** として、この業界に実際に属している。

| 他の創業者がいない理由 | 堀越が持つもの |
|---|---|
| 施工現場を知らない → 課題設定がずれる | 毎日この業務をやっていた一次情報 |
| 保険会社との接点がない | 施工店として損保との書類やり取りを経験済み |
| 顧客ニーズが仮説 | 自分が顧客。検証コストがゼロ |
| 業界ネットワークを作れない | `detailing_holy` ブランドで施工業界との接点保有 |

**これは「施工業界に詳しい人がソフトウェアを作った」ではなく、「施工店が自分のために作ったソフトウェアを他の施工店に売っている」という構造。** この違いは決定的。

### 1-2. 「ドッグフーディング」が最速の製品改善サイクル

Ledra は `detailing_holy` で実際に使われているプロダクト。

- 施工店として自分が使って痛みを感じたら即修正
- 顧客への証明書発行・LINE 通知・保険会社向け書類送付を **自社で毎日テスト**
- 「機能を作って仮説検証する」のではなく「自分が困っているから作る」

この開発サイクルは、市場調査から始める SaaS スタートアップには再現不可能。

## 2. 実行証拠: 「プロダクトがある」という事実の重み

Why Us を語る際に最も強力な根拠は、**プロダクトが既に動いていること**。

### 2-1. 技術的実装の規模

| 指標 | 値 | 意味 |
|---|---|---|
| API エンドポイント | **482 本** | 4 ポータル × 深い機能を全て API 化済 |
| データベース Migration | **239 本** | 2 年以上の継続開発の証拠 |
| テストケース | **2,100+** | 本番品質のコードベース |
| 主要連携 | Stripe / Square / Polygon / LINE / CloudSign / Google / Supabase | 国内 SaaS として必要な主要連携を網羅 |
| 特許出願準備 | 3 件 (`docs/patents/`) | 車両パスポート・写真改ざん検知・AI自動化ガードレール |

これは「デモ」ではなく「本番稼働している製品」の数字。

### 2-2. 本番稼働の事実

- 2026 年 4 月: 施工店 6 店舗で本番稼働開始
- 証明書発行・Polygon アンカリング・顧客ポータル・保険会社ポータルが実際に動作
- Apple Pay / Square Terminal による現場 POS を実装・稼働
- iOS / Android モバイルアプリを公開

**BMW VerifyCar が 6 年 PoC のまま、Toyota Blockchain Lab がテックペーパー段階のとき、Ledra は本番稼働している。**

## 3. 参入障壁: なぜ後発が追いつけないか

### 3-1. 日本固有インテグレーションの蓄積

後発が 2〜3 年かかる実装が既に完了している:

| 機能 | 後発のコスト | Ledra の現状 |
|---|---|---|
| 車検証 OCR (IC チップ対応) | 国交省の仕様書解読 + 実装 6〜12ヶ月 | **実装済** |
| CloudSign 電子契約連携 | API 交渉 + 法務確認 3〜6ヶ月 | **実装済** |
| LINE Messaging API 連携 | 要件整理 + 実装 2〜3ヶ月 | **実装済** |
| 特商法・インボイス制度対応 | 法務確認 + UI 設計 3〜6ヶ月 | **実装済** |
| 法人番号検索 (Insurer 登録) | 国税庁 API 実装 1ヶ月 | **実装済** |
| Polygon アンカリング | ブロックチェーン設計 + セキュリティ審査 3〜6ヶ月 | **実装済** |

### 3-2. マルチロール構造の複雑性

Ledra は **Admin / Agent / Insurer / Customer の 4 ロール**を同一プラットフォームで管理する B2B2B2C 構造。

- 施工店だけを作るなら参入容易
- 保険会社ポータルを別途作るなら参入容易
- **4 ロールを 1 プラットフォームに統合し、テナント分離・RLS・マルチテナント課金を正しく実装する**のは 1〜2 年の開発量

### 3-3. 証明書の累積発行数がデータ堀になる

施工証明書は **発行した枚数が積み上がるほど、保険会社・中古車ポータルへの参照価値が高まる**。

- 後発が同じ機能を作っても、累積データがなければ保険会社は採用しない
- 先行者が「10 万枚の施工証明書を持つプラットフォーム」になると、後発がゼロから同じ立場を得るのは不可能

## 4. Why Us の 4 層構造 (ピッチ用)

VC への説明は以下の 4 層で構造化する:

```
Layer 1: Founder-Market Fit
  「施工店オーナー出身。自分の課題を解いている。一次情報の優位は買えない。」

Layer 2: 実行証拠
  「482 API / 239 migration / 2,100+ tests。2年かけて作った本番稼働プロダクト。
  BMW が6年かけて未実装なものを、Ledra は動かした。」

Layer 3: 参入障壁
  「日本固有連携の実装済みセット。4ロール統合の開発量。
  後発が追いつくには最低 2 年 + 施工業界の一次情報が必要。」

Layer 4: ネットワーク効果のタイミング
  「証明書の累積発行数が堀になる前に、保険会社との接続を確立する。
  このタイミングを逃すと後発には取り返せない。」
```

## 6. 想定 Q&A (VC 向け Why Us 質問対策)

### Q: 「大手 SaaS (kintone 等) が同じ機能を作れば終わりでは?」

**A**: kintone は汎用ローコードであり、施工業界特有の「証明書 × NFC × 保険会社 API × Polygon」という組み合わせを本気で作りに来る理由がない。TAM が小さすぎる (コーティング専業 5,000 店) と見えるから。逆に Ledra は、この狭いエントリーから保険会社・中古車流通という大きな市場に接続する設計。大手が参入した時点で Ledra はすでにネットワーク効果で堀ができている。

### Q: 「Shopmonkey が日本参入したら?」

**A**: 参入しても日本固有連携 (車検証 OCR / CloudSign / LINE / 保険会社 API) の再実装に 1〜2 年かかる。その間に Ledra は保険会社 × 代理店のエコシステムを確立する。Shopmonkey が国内で代理店網と保険会社接続を持つには、さらに 2〜3 年の業界浸透が必要。合計 3〜4 年の猶予がある。

### Q: 「なぜ堀越さん個人の会社なのに 10億 ARR が狙えるか?」

**A**: 3 階建て ARR の第 2 階 (保険会社 ¥3 億) と第 3 階 (流通 ¥1 億) は、施工店を 2,400 店取らなくても成立する。保険会社 3 社が本番接続すれば、それだけで ¥3 億規模になる。B2B エンタープライズ課金のレバレッジが、「小さなチームでも大きな ARR が作れる」根拠。

### Q: 「創業者依存のリスクは?」

**A**: 現状、プロダクトの企画・実装に CEO が深く関与していることは事実。これが採用が最重要な理由であり、調達後の使途の筆頭が CTO 採用。ただし現時点でも 2,100+ テストと 239 migration が存在し、新しいエンジニアが参加できる状態のコードベースになっている。
