## 「“連携できたら送る”をどこに置くか」— 通知の起点は画面ではなく、事実

- 状態: 未着手
- メモ: 公開可（設計判断のみ。顧客データ・実テナント・実URLは載せない）。キーメッセージ:「症状が出た経路ではなく、事実が成立する場所を直す。」「無料で届けられる経路があるなら、わざわざ有料で送らない。」「送れない条件では黙って送らない——壊れたリンクは無通知より悪い。」

## 「インフラを疑って半日、真因は `Number("")===0` の1行だった」― 帳票が全部消えたデバッグ記
- 切り口: 本番で帳票一覧が突然0件に。DBには28件ある、権限(service_role)も接続先も環境変数も正しい——なのにアプリ経由だけ0。RLS・接続プールの過渡的不具合・環境変数ミスと順に疑い、リトライで“温める”対症策まで入れたが直らなかった。決め手はサーバのAPIログで「実際に飛んでいるクエリ」を1行見たこと。そこには誰も指定していない `total>=0 AND total<=0`(＝total=0) という金額フィルタが常時付いていた。原因は「金額の検索欄が未入力のとき `Number("")` が 0 になる」JavaScriptの挙動。空を『フィルタ無し』ではなく『0で絞り込み』と解釈し、金額>0の全帳票を弾いていた。教訓は3つ:「インフラを疑う前に“実際に発行されたクエリ”を見る」「症状(0件)に対症療法(リトライ)を積むと真因から遠ざかる」「`Number(空文字)===0` は定番の罠——空判定を先に書く」。AIと高速に実装を回すからこそ、症状ではなく一次ソース(ログ・実クエリ)で真因を掴む規律が要る、という話に接続できる。
- 想定読者: Web/SaaS を本番運用するエンジニア、小さなチームで自分でデバッグする開発者、AIコーディングを実務で使う人。
- 状態: 未着手

## 「セキュリティ対策のはずが、本番だけ壊す」― DB関数の search_path='' が両刃だった話
- 切り口: Supabase/Postgres の SECURITY DEFINER 関数には `SET search_path=''` を付けるのがセキュリティ定石（search_path ハイジャック対策）。だが `search_path=''` は「関数本体のテーブル参照を全部スキーマ完全修飾している」ことが大前提で、本体が非修飾のままだと逆に本番で必ず `relation does not exist` を吐いて壊れる。実際、対策を一括で付けた際に本体の修飾を直し忘れた関数が数か月放置され、証明書統計や保険会社ポータルが静かに失敗していた。しかも直すと今度は「enum に無い値を参照していた」二次バグが露出。教訓は「セキュリティ設定はそれ単体では完成せず、前提条件（完全修飾）とセットで初めて安全」「一括対策こそ取りこぼしが起きやすく、後追い検証が要る」。AIと現場でコードを高速に回すからこそ、こうした“設定の前提”を検証する仕組みが要るという話にもつなげられる。
- 想定読者: Supabase/Postgres を本番運用するエンジニア、SECURITY DEFINER を使う開発者、小さなチームでDBを触る人。
- 状態: 未着手
- メモ: 対象4関数、二重バグ（バレ参照→enum 'expired'）、既存の確立パターン（status::text 比較）に寄せて最小差分で修正。具体的な本番プロジェクトIDや統計値は載せない（技術的教訓のみ公開可）。

## 「電話で枠を押さえる」をやめる ― 二重押さえを防ぐ仮押さえの作り方
- 切り口: 取引先に作業を頼むとき「今週空いてる？」の電話が現場を止める。Ledra では取引先の空きをアプリで見て
  枠を仮押さえ→相手が受注承認で本予約、という流れにした。技術的な肝は「二店が同じ最後の1枠を同時に押さえる」
  競合を防ぐこと。素朴な『空き数を数える→入れる』は非原子で競合窓があるため、DB の advisory lock で
  (店舗,日,枠) ごとに直列化し、占有（既存予約＋有効な仮押さえ）を数えてから入れる、を1関数に閉じ込めた
  （社内の会計番号採番で使っていた手法の再利用）。「新機能はまず既存の手法を探して流用する」設計の実例。
- 想定読者: 予約・在庫など"最後の1個"競合を扱うプロダクトの開発者、B2B 連携を作るチーム。

## 「返信は返したのに処理が消える」― サーバーレスの fire-and-forget 落とし穴

- 切り口: LINEの自動応答のように「まず200を即返し、重い処理は裏で続ける」構成は、
  サーバーレス環境だとレスポンス送出後に裏処理が無言で打ち切られることがある。Ledraでは
  予約確定時の会計提案・カレンダー同期が撃ちっぱなし（未await）で走っており、

  await して完走を保証する形に直した実例。「裏で流しておけば大丈夫」がなぜ危ういかを、
  テストで再現（撃ちっぱなしだと落ちる回帰テスト）まで含めて説明できる。
- 想定読者: 業務システム／SaaSを作る開発者、サーバーレス移行を検討中のチーム。
- 状態: 未着手
