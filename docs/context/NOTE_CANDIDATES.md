## 壊れた監視 cron を「鳴らし続ける」のをやめる ― 設定ミスは skip、本物の障害だけ通知する
- 切り口: 残高監視 cron が、秘密鍵の些細な形式ミス（`0x` の付け忘れ）で510回超も「失敗」を鳴らし続けていた。
  修正は"リトライを足す"ことではなく「失敗の種類を分ける」こと ― 設定ミスは skip して失敗連鎖に積まず、本物の
  RPC 障害だけ通知する。ついでに直す場所を「呼び出し元」ではなく「共有関数」にして、監視とアンカリング署名の
  両方を一度に直した話。
- 想定読者: 監視/アラートを運用する開発者、cron・バッチの失敗設計に悩む個人〜小規模の運用者。
- 状態: 未着手
- メモ: 教訓は2つ ―（1）アラート疲れは「全部を失敗として鳴らす」設計から生まれる、種類を分ければ止まる。
  （2）バグは症状（呼び出し元）でなく根（共有関数）で直す。※ 秘密鍵の値・ウォレットアドレス・アンカリング基盤の
  具体は書かない（機密）。公開区分は「要確認」。

## 「放送と同時に記事を出す」ために予約投稿を自作した ― 5分おき cron ＋ 非公開を RLS で担保
- 切り口: 令和の虎の放送(土19:00)に記事を"同時に"出したいが、手動公開は放送時刻に人が張り付く前提で不確実。
  そこで CMS に予約投稿（`scheduled` ＋ 公開日時 ＋ 5分おき cron で自動昇格）を1本の cron で足した話。ポイントは
  「予約中に絶対に漏らさない」を機能ではなく DB の公開ポリシー(RLS: published のみ読める)で構造的に担保したこと。
  記事は放送5分前(18:55)に自動公開されるよう仕込んだ。
- 想定読者: 個人〜小規模で自社プロダクトを回す開発者、CMS/publishing を自作している人。
- 状態: 未着手
- メモ: おまけの"war story"として、予約用マイグレーションが本番で連続失敗→真因は別々の PR が同じ version 番号を
  使った衝突＋本番への out-of-band 適用ドリフト、を「本番記録に合わせて改名(forward)」で解いた話も書ける。
  「マイグレーションの唯一の真実は本番スキーマ」という教訓。機密・個人情報は書かない。保険会社提携等の非事実も書かない。

## LINEの「初手で連携をお願いします」がお客様を逃す ― オンボーディングの引き算

- 切り口: LINE公式アカウントは店から先に送れず、必ずお客様発でやり取りが始まる。だからこそ最初の数通が勝負で、

- 状態: 未着手
- メモ: 変更は送信タイミングの既定値のみ（env で店ごとに調整可能）。数字(2→4)の最適値は実運用の離脱率/連携率で要検証。

## 「同業者に電話で頼む」をやめる ― 加盟店同士が手数料0で仕事を回す仕組み

- 想定読者: 整備・鈑金・コーティング等の工場経営者、多店舗連携を模索する事業者、B2B SaaS を作る開発者。

## 「電話で枠を押さえる」をやめる ― 二重押さえを防ぐ仮押さえの作り方
- 切り口: 取引先に作業を頼むとき「今週空いてる？」の電話が現場を止める。Ledra では取引先の空きをアプリで見て
  枠を仮押さえ→相手が受注承認で本予約、という流れにした。技術的な肝は「二店が同じ最後の1枠を同時に押さえる」
  競合を防ぐこと。素朴な『空き数を数える→入れる』は非原子で競合窓があるため、DB の advisory lock で
  (店舗,日,枠) ごとに直列化し、占有（既存予約＋有効な仮押さえ）を数えてから入れる、を1関数に閉じ込めた
  （社内の会計番号採番で使っていた手法の再利用）。「新機能はまず既存の手法を探して流用する」設計の実例。
- 想定読者: 予約・在庫など"最後の1個"競合を扱うプロダクトの開発者、B2B 連携を作るチーム。
- 状態: 未着手
- メモ: DECISION_LOG.md 2026-07-20「他店の空き確認＋枠押さえ(Phase 2)」が一次材料。特定店舗の空き・取引額・
  個人情報は載せない。プライバシー(誰に空きを見せるか)は「取引先=許可制」に留めた点も語れる。

## 「終日お預かり」をどう予約に落とすか ― 既存の暗黙ルールに逆らわない機能追加
- 切り口: コーティングやPPFのように「朝預けて夕方引き取り」の1日仕事を、時間枠だけの予約システムに
  後付けで載せる話。素直に 00:00〜23:59 の枠として保存する手もあるが、Ledra は元々「時刻が空＝終日」を

- 想定読者: 予約・スケジュール系のプロダクトを作る開発者、機能追加で技術的負債を増やしたくないチーム。
- 状態: 未着手

## 「返信は返したのに処理が消える」― サーバーレスの fire-and-forget 落とし穴

- 切り口: LINEの自動応答のように「まず200を即返し、重い処理は裏で続ける」構成は、
  サーバーレス環境だとレスポンス送出後に裏処理が無言で打ち切られることがある。Ledraでは
  予約確定時の会計提案・カレンダー同期が撃ちっぱなし（未await）で走っており、
  Next.jsの `after()` に載せた後も「外側が先に終わると中の未完了処理が捨てられる」問題が残っていた。
  await して完走を保証する形に直した実例。「裏で流しておけば大丈夫」がなぜ危ういかを、
  テストで再現（撃ちっぱなしだと落ちる回帰テスト）まで含めて説明できる。
- 想定読者: 業務システム／SaaSを作る開発者、サーバーレス移行を検討中のチーム。
- 状態: 未着手
- メモ: DECISION_LOG.md 2026-07-18「LINE予約枠確定の背景処理は…after()内でawait完走」エントリが
  一次材料。特定テナントの数値・個人情報は含めない。技術ネタなので事業機密には触れない。
