## 「アプリのどこからも呼ばれていない」を「消していい」と読んだ

- 何があったか: 設計図に無いまま本番で動いていたテーブル23本を消そうとした。
  事前にアプリのソースを全文検索して、**参照ゼロ**を確認していた。行数も23本合わせて2行。
  「未使用。消して安全」と書いて、その分類を公開もした。
- 何が起きていたか: 消す直前にデータベース側の依存関係を引いたら、外れていた。
  アプリからは呼ばれていないが、**データベースの内側から使われていた**。
  3本のテーブルを5つの関数が読み、その関数を**26本のアクセス制御ルール**が使い、
  さらに1つは**ファイルストレージのアクセス制御**からも使われていた。
  そのまま消していたら、消すつもりのなかった場所が道連れになっていた。
- なぜ気づけなかったか: 「使われているか」を確かめる経路が5つある
  （アプリのコード / アクセス制御ルール / 関数の中身 / 外部キー / 別領域）のに、
  **1つ目だけを見て全体の結論にした**。しかも1つ目の観測自体は正しかった。
  **観測が正しいことと、その観測が問いに答えていることは別。**
  問いは「消して安全か」で、ソース検索が答えられるのは
  「アプリのコードが壊れないか」だけだった。
- 直し方: 消す前にデータベースに直接「これに依存しているものを全部出せ」と聞く。
  1回の問い合わせで5経路がまとめて出る。検索は補助に落とす。
- 結論: AI に作業させるときに効く教訓でもある。**AI は「grep してゼロ」を
  自信を持って「未使用」と言い換える。** 言い換えた瞬間に、
  何を見てそう言ったかが消える。「未使用」と書くときは、
  同じ文に「何を見てそう言えるのか」を書かせるとよい。書けなければ根拠が足りない。
- 併せて: この件は、同じ日に「設計図と本番が69個ずれている」と報告した、その続き。
  ずれを直そうとして、**直す側の判断がまたずれていた**。
- 公開区分: 公開可（テーブル名・件数のみ。データの中身・個人情報を含まない）
## 「見守り役」を作った初日に、その見守り役自身が3件の事故を止めた

- 切り口: レビュー待ちが長くなった変更の日付を毎日見回るだけの自動チェックを作った。
  やることは日付の比較ひとつで、判定ロジックは1行も書いていない
  （**既にある検査を、別のタイミングで回すだけ**）。初日の実行で**3件**引っかかり、
  うち2件は**11分以内に直った**。
- なぜ効いたか: 検査の中身はもともと正しかった。壊れていたのは**タイミング**だけ。
  「変更を出した瞬間には正しかった日付が、待っている間に追い越される」——
  ところが**待っている間は検査が動かない**。だから誰も気づかないまま数日が過ぎる。
  足したのは新しい判定ではなく、**同じ判定をもう一度回す機会**だった。
- 学び1: **同じ事故が繰り返すとき、疑うべきは検査の中身とは限らない。**
  「検査は正しいのに事故が起きる」なら、検査が**いつ動くか**を見る。
  中身を厳しくしても、動かない時間帯があるならそこは素通しのまま。
- 学び2: 判定を2箇所に書くと、必ず片方だけが直る。**新しい見張りには判定を書かず、
  既にある検査をそのまま呼ぶ。**
- おまけ（正直に）: その見守り役自身に後始末のバグがあり、2件目以降の検査結果に
  1件目のファイルが混ざっていた。**今回それが誤報にならなかったのは、たまたま
  対象が全部本物だったから。** 見張りを作ったら、見張り自身を見張る必要がある。
- 状態: 未執筆
- 公開区分: 公開可（自動化設計の一般的な教訓。リポジトリ名・PR 番号・内部構成は書かない）

## 「送信しました」と出る画面が、お客様には届いていなかった話
- 切り口: 会計後にレシートをお客様へ送る機能を点検したら、**送ったリンクが必ずエラー画面に
  なっていた**。店側の画面には「送信しました」と出る。SMS アプリを開くところまでは成功するので、
  **壊れているのは受け取った側だけ**。誰も報告しないまま動き続けていた。
  原因は、URL を組み立てる1行が**別の書類の公開ページ**を指していたこと。
  さらに私は、その壊れた1行を新しい画面にコピーして**壊れ方を2箇所に増やしていた**。
  変数の名前が「レシートのURL」で、値が自社のドメインで始まっていたので、
  中身を確かめずに「動いているものを再利用した」つもりになっていた。
- 学び: **コピーは「動いている証拠」ではない。** 既存コードを持ってくるとき、
  「これは動いているはずだ」の根拠は「そこに書かれていたから」でしかないことがある。
  特に**送信先が外にあるもの**（メール・SMS・Webhook・QR）は、送る側の画面が
  成功と出ても受け取る側が壊れていることがある。**成功の判定が送信側にしか無い機能は、
  受け取り側を一度は自分で開く。**
  対策として、URL の組み立てを1箇所に集め、**行き先を自動テストで固定した**
  （書き換えるとテストが落ちる）。文字列を画面に直接書かない限り、次は同じ形にならない。
- 公開区分: **公開可**（ドメイン名・ルート名・テナント名・トークンの実値は書かない）

## 新しいものを置く前に、隣に何があるか見る
- 切り口: 新しい公開ページを作るとき、置き場所に**既に別のものが入っていた**。
  仕組み上そこには1種類しか置けないので、そのままだとビルドが通らない。
  同じ日に同じ形のミスをもう1回した ―― 部品を1箇所にまとめようとして新しいファイルを作ったが、
  **まとめ先のファイルは既に存在していた**。どちらも一覧を1回見れば分かる話だった。
- 学び: 型チェックもテストも全部緑だった。**どちらの誤りも型に現れない。**
  片方はビルドでしか出ず、もう片方はそもそも壊れていない（ただの重複なので誰も落ちない）。
  「緑だから大丈夫」が2回とも通ってしまう。
  習慣にしたのは2つ。**新しいファイルを作る前に、置くディレクトリの中身を見る。**
  **公開前にビルドを1回通す**（型チェックとテストでは出ない種類の壊れ方があるため）。
- 公開区分: **公開可**

## 「オフにする」設定が存在しないとき — ライブラリの想定外を、設定で殴らずに回避する

- 切り口: アプリの起動画面を「ロゴなしの単色」にしたかったが、使っているフレームワークには
  その設定が無かった。画像を指定しなければロゴは出ない、と思って消したら、
  画面の定義ファイルにはロゴへの参照だけが残り、参照先が無いのでビルドが落ちた。
  ソースを読むと「参照を書く処理」と「実体を書く処理」で条件分岐が食い違っており、
  さらに「昔の挙動に戻す」分岐は `null` と `undefined` の取り違えで**到達不能**になっていた。
  解決策は「背景と同じ色の画像を渡す」。オフにできないなら、
  オンのまま見えなくすればいい。フレームワークにパッチを当てるでも、
  依存を増やすでもなく、1902バイトの単色画像1枚で済んだ。
- 想定読者: OSS のフレームワーク上でプロダクトを作っている開発者
- 状態: 未着手
- メモ: 整備でも同じ判断をする。「そのスイッチは存在しない」と分かったとき、
  配線を切って無理やり止めるのか、動いたまま影響が出ない状態にするのか。
  後者の方が壊れにくいことが多い。
  材料: 該当コードの条件分岐（参照側は無条件、実体側は `if (image)` で保護）、
  `null !== undefined` で死んでいる分岐、透明ではなく同色にした理由
  （空アイコンをアプリアイコンで置き換える端末実装がありうる）。
  検証として「事故そのものを再現して検査が落ちること」を確認した手順も書ける。
- 公開区分: 公開可

## CIが全部緑なのに本番ビルドが落ちる — 「静的に分かることは静的に止める」

- 切り口: モバイルアプリの Android ビルドが「一度も通っていなかった」ことに、
  実機確認を始めて初めて気づいた話。決済端末ライブラリが Android 8.0 以上を要求しているのに、
  アプリ側の設定が 7.0 のままだった。この矛盾は設定ファイルを2つ見比べれば数秒で分かるのに、
  17分かけてビルドが失敗するまで誰も気づかなかった。CI は型チェックとテストだけを回していて、
  ネイティブの設定は一切見ていなかったため。フルビルドを CI に載せる（1回20分）のではなく、
  設定の整合だけを数秒で検査する仕組みを足して決着させた判断。
- 想定読者: モバイルアプリを内製している開発者 / 小規模チームで CI を設計する人
- 状態: 未着手
- メモ: 整備の世界にも同じ構造がある。「エンジンをかけてみないと分からない不具合」と
  「点検表を見比べれば分かる不具合」は別物で、後者を試運転で見つけるのは時間の使い方として間違っている。
  数字: ビルド失敗 2回（16分58秒 / 11分47秒）に対して、追加した検査は GitHub Actions 実測で
  prebuild 3秒＋検査 1秒未満（CI ジョブ全体で 39秒）。桁が3つ違う。
  検査を入れる前の状態を再現して、実際に落ちることを確認してから採用した点も材料になる。
- 公開区分: 公開可

## 「保存して速くする」が正解とは限らない — 演出の尺が設計判断を変えた話
- 切り口: アプリ起動時のちらつきを「値をディスクに保存すれば直る」と考えたが、
  調べると**保存で稼げる時間の使い道が無い**ことが分かった、という話。
  直前に入れた起動アニメーションが1.85秒の下限を持っていたため、保存で短縮できる
  ネットワーク1往復はその尺に完全に隠れる。利得ゼロ。
  一方で保存の代償は具体的に5つ数えられた。ログアウト経路の1つが店舗選択を消さないので
  セッションより長生きする、無効化された店舗に固定されるとエラーも出ずに全タブが空になる、
  正規化なしでINSERTしている3箇所がFK違反を起こす、など。
  結論は「保存して速くする」ではなく「毎回取り直すが、見えない時間に隠す」。
  往復の総数は同じで、見える位置だけが変わる。
  一般化すると「最適化の利得は、それが露出する場所があって初めて価値になる」。
  同じ最適化でも、手前に1.85秒の演出があるかないかで正解が入れ替わる。
- 想定読者: 個人開発者 / パフォーマンス改善をやる人 / SaaS のPM
- 状態: 未着手
- メモ: 「よく知られた正解（キャッシュする・永続化する）を、自分の状況で採点し直す」が主題。
  代償を5つ数えて並べたら判断が一瞬でついた、という点も書ける。
  変異テストで「2件以上でもデフォルト店舗を選んでしまう」バグを検出できることを
  確認した話も繋げられる（親切心で壊れやすい箇所を固定する）。

## 「CIは全部緑」でも、本番と設計図は 68 個ずれていた

- 何があったか: 「使われていない権限テーブルが本番にだけ在り、マイグレーション（設計図）に
  定義が無い」という事故の後始末で、**同じことが他にも起きていないか**を機械的に数えた。
  結果、テーブル23・ビュー1・関数24・トリガ15・型5 の**計 68 個**が、
  設計図に無いまま本番で動いていた。
- なぜ検査をすり抜けたか: 検査は2つあった。どちらも**この形のずれを見ない作り**だった。
  - 設計図の再生検査 — 空のデータベースに設計図を全部流して「エラーが出ないか」を見る。
    **できあがったものを本番と比べていない**ので、本番にだけ在る物は原理的に出ない。
  - スキーマ照合検査 — 照合の基準を**本番からコピーして**作っている。
    ずれごと写して合格する。
  つまり「緑」は「設計図に矛盾が無い」であって、「本番が設計図どおり」ではなかった。
- 危険度は2つに割れた: **テーブル23個は無害**だった（21個が0行、アプリからの参照ゼロ、
  全件アクセス制御が有効）。危なかったのは**関数**で、設計図に無い関数5本を
  **35本のアクセス制御ルール**が呼んでいた。**設計図だけから作り直したデータベースは、
  本番と同じ権限判定をしない。** 復旧のときに初めて分かる種類の欠落である。
- 何が言えるか: 検査の緑は「何を比べたか」以上のことを保証しない。
  **「本番と設計図が一致しているか」を比べる検査は、意外とどこにも無い。**
  作った当人は「マイグレーションで管理している」と思っているし、
  ダッシュボードで1回手を入れたことは半年後には誰も覚えていない。
- 公開区分: 公開可（テーブル名・件数のみ。データの中身・個人情報は含まない）

## テストは緑、機能は壊れていた — 「その語が書いてある」を「そう動く」と読んだ

- 何があったか: 「AIが作った文面を、人が公開前に目視確認する」仕組みを作った。確認が今も有効かを
  表す印を作り、生成側と公開側で突き合わせる。印に版の情報が入っていることをテストで固定し、
  **壊すと落ちることも確かめた**。緑だった。自動レビューが指摘した ——「その状態では、
  公開が1件も通りません」。
- 何が起きていたか: 印は片側が**プログラムが作った時刻の文字列**、もう片側が**データベースが
  返した時刻の文字列**から作られていた。同じ瞬間なのに表記が違う（末尾が `Z` か `+00:00` か）。
  ハッシュは永久に一致しない。**確認しても必ず「内容が最新ではありません」で弾かれる。**
- なぜ緑だったか: テストが確かめていたのは「その関数の中に、版を表す語が**書いてある**」ことだけ。
  **生成側と公開側が同じ値を渡すかは、一度も走らせていなかった。** ソースを検索する形の検査は、
  文字列の有無しか語れない。片方が `Z`、片方が `+00:00` でも緑のままである。
- 効かなかった対策: 「検査を壊して落ちることを確かめる」は実施済みだった。だがそれで分かるのは
  **文字列の変化を検出できる**ことだけで、**その文字列が正しい動作を意味するか**は出てこない。
- 直し方: 表記を揃えるのではなく、**両側の出所を揃えた**。片方が「送った値」、もう片方が
  「返ってきた値」になっている構造そのものが原因で、同じ罠は時刻以外の項目にも残っていた。
- 結論: 「書いてある」と「そう動く」の間には距離がある。**構造を見る検査を書いたら、
  「これが緑のまま壊せる形」を1つ挙げてみる。** 挙げられたら、その形を潰す検査をもう1本足す。
  AI に開発させる文脈で特に効く —— AI は緑を完了の合図として扱いやすい。
- 併せて: 自動レビューは4巡し、うち1巡は**私が直した結果できた穴**を突いた。直したことより、
  直した後にもう一度見てもらうことに価値があった。
- 公開区分: **公開可**（技術的な一般論のみ。店名・顧客情報・自社の権限構成・
  取引先には触れない。使用したレビューツール名は伏せて「自動レビュー」と書く）
- 状態: 未執筆

## 「日付を確かめる」だけの自動チェックが、書き込み権限の受け渡し口になっていた
- 切り口: レビュー待ちが長くなった変更を毎日見回って、日付のズレを知らせるだけの
  自動チェックを作った。やることは日付の比較ひとつ。危ないことは何もしていない、
  つもりだった。
- 実際にやっていたこと: そのチェックは**相手が書いたプログラムを、こちらの権限で
  実行していた**。相手のファイルを持ってきて、そのまま動かす作りだったため。
  日付を見るだけのはずが、「うちの鍵を渡して好きに動かしてもらう」形になっていた。
- もう一つの副作用: 動かしていたのが**相手側のチェック**だったので、
  相手が「問題なし」と言えばそれが通る。**見張りたかった相手に、
  自分が問題ないかを自己申告させていた。**
- なぜ気づけなかったか: **「何を実行するか」は考えたのに、「誰が書き換えられるものを
  実行するか」を考えなかった。** 手元で同じ操作をすると自分のファイルが出てくるので、
  差が見えない。自動化した瞬間に、同じ操作が別の意味になる。
- 直し方: 相手のプログラムは持ってこない。**必要なのはデータ（日付）だけ**なので、
  データだけを取り出して、こちら側のプログラムで読む。
- 学び: 自動化を1つ足すときは、**「この処理の権限で、誰の書いたものが動くか」を

## AI に開発させるとき、いちばん検証されないのは「AI が判断に使った道具」

  おまけに、サーバ側の“正しい処理入口”は元々あったのにアプリから呼ばれておらず、しかも旧経路は
  存在しない保存先に書いていて動いていなかった——「1系統に寄せる」設計整理の教訓も材料。
- 想定読者: 車・整備/コーティング業界の経営者 / 証拠性・改ざん対策を気にする実務者 / 小さく作るSaaS開発者
- 状態: 未着手
- メモ: 具体的なプロジェクトID・スキーマ内部・匿名キー等の機密は書かない。真正性グレードの内部名や
  端末アテステーションの実装詳細も伏せ、「その場撮影・端末非保存・後からDL」という体験の骨子に絞る。

## 「カテゴリと検索を足しても羅列は直らなかった」——原因は並べ方と描画量だった話
- 切り口: 「品目一覧が無造作な羅列」と言われて、カテゴリ分けと検索を足した。次のテストでまた同じ指摘。
  原因は絞り込み機能の不足ではなく、(1) 品目名の長さで幅が決まるボタンを折り返し配置していたこと、
  (2) 全品目を一度に描画していたこと、の2つだった。周辺を足しても、原因に触れなければ症状は残る。
  等幅タイルのグリッドと画面分だけ描く仕組みに変えたら、同じ機能のまま印象が変わった。
- 想定読者: 小さく速く作る SaaS 開発者 / 現場で使う業務アプリを内製している人
- 状態: 未着手
- メモ: 「言われた機能を足す」と「言われた不満の原因を直す」は別物、という一般論に落とせる。
  具体的な品目名・価格・店舗名は書かない。

## 「タブが5枚だと、+ ボタンは真ん中に置けない」——UIの選択肢を決めるのは幾何の制約
- 切り口: 「タブを丸くして、センターに+ボタン」と言われた。だがタブが5枚あると、+ を列の中に入れた瞬間
  6スロットになり、どこに置いても中心は 41.7% か 58.3% にしかならない。真ん中に置ける形は
  「タブを4枚に減らす」か「列の上に浮かせる」の2つだけ。今回は5枚目のタブが15本の導線を持つハブだったので、
  減らさずに浮かせた。デザインの要望が物理的に何を要求しているかを先に計算すると、選択肢が2つに絞れる。
- 想定読者: プロダクト志向の経営者 / デザインと実装の間で判断している人
- 状態: 未着手
- メモ: 「できません」ではなく「この形なら成立し、代償はこれ」と出す進め方の実例。アプリの内部構成の
  細部（画面名の羅列など）は書かない。

## 「自分が書いたコードにレビューをかけたら、実害4件が出てきた」
- 切り口: UI改修を書き上げて型チェックもテストも通った状態で、自動コードレビューを回した。出てきたのは

## 「3回直して3回とも直らなかったバグ」——修正が届いていない場所に書かれていた話
- 切り口: 「戻るボタンが出ない」と3回言われた。1回目も2回目も、正しい形の修正コードを書いていた。
  問題は書いた場所で、同じ画面のファイルが2つあり、自分が直した方は表示されない側だった。
  症状（ボタンが無い）に対して正しい対策（ボタンを足す）を打っても、対象が違えば0点。
  3回目でようやく「なぜ効かないのか」を先に調べ、重複そのものを消して解決した。
  同じコードを8箇所に手書きしていた構造も、書き漏らしを生む温床として共有化した。
- 想定読者: 小さく速く作る SaaS 開発者 / AIにコードを書かせている実務者 / 現場で内製している人
- 状態: 未着手
- メモ: 「直したのに直らない」ときは、修正内容ではなく修正が届いているかを疑う、という教訓に落とせる。

## 「判定ロジックはあるのに、誰も呼んでいなかった」——発行ゲートを4つの経路に配線し直した話
- 切り口: 「証明書の発行は◯◯条件を全部満たさないとダメ」というルールを判定する関数は、テスト付きで
  ちゃんと実装されていた。ところが実際に証明書を「発行済み」にする4つの入口（管理画面・アプリ・
  オフライン経路・AI自動発行）は、どれもその関数を一度も呼んでいなかった——写真の有無だけを
  それぞれが個別に手書きでチェックしていた。「型やロジックを作った」と「実際に使われている」は別物。
  配線し直す過程で、別の判定（署名依頼）が「証明書が発行済みであること」を前提にしている設計と
  正面衝突することも判明した。発行→署名→発行という無限ループになりかねない箇所で、配線する前に
  気づけたので事なきを得た。
- 想定読者: 小さく速く作る SaaS 開発者 / AIにコードを書かせている実務者 / 業務システムを内製している人
- 状態: 未着手
- メモ: 「ロジックが存在する」と「呼ばれている」の間には検証しないと埋まらないギャップがある、という
  一般論に落とせる。加えて、AIによるコードレビューで「4つの入口のうち2つでは、条件の一部が
  実は素通りしていた」という見落としも見つかった（懸念の紐付け方が経路によって違っていた）——
  自分で書いたロジックを自分でレビューしても見えない穴がある例として使える。具体的なテーブル名・
  関数名・社名は書かない。
