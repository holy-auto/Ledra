## 「真正性チェックはデフォルト無害に設計する」― 誤検知で現場を止めないAI真正性の作り方
- 切り口: 写真の位置情報や電子署名で「本物かどうか」を裏で確認する仕組みを足すとき、検出したら強く警告するほど良いと思いがち。だが出張作業がメインの現場では「店舗から離れた場所で撮影」が普通で、そのまま警告すると毎回誤報になる。そこで (1) 既定設定では余計なフラグを一切増やさない「デフォルト無害」、(2) 改変が確定的なものだけを"要対応"、位置ズレ等は"要確認"止まりで作業を止めない、(3) 生の位置座標は保存せず照合結果だけ残す、(4) 画像を見ても判断できない項目（位置・署名）はわざわざAIに再確認させず無駄なコストを出さない、という設計原則で「真正性は上げるが現場・プライバシー・コストは壊さない」を両立した話。出張現場は端末GPSを作業記録に紐づけて"正当な場所"として扱う。
- 想定読者: 現場業務にAI検証を足すプロダクト開発者・PM、誤検知の運用コストに悩むチーム。
- 状態: 未着手
- メモ: 競合の実名は書かない。一般化した設計原則（デフォルト無害／非決定的優先／生データ非保存／無駄な推論を呼ばない）に留める。裏付けは RELEASE_LOG / DECISION_LOG 2026-07-27 フェーズ2エントリ。公開区分＝公開可（一般的な設計知見）。

## 位置情報は「使うけど残さない」― プライバシーを守りながら写真の撮影場所を検証する
- 切り口: 施工写真には撮影場所（GPS）が埋まっていることがあり、顧客の自宅位置になり得るため保存は避けたい。一方で「その写真が本当に作業場所で撮られたか」の確認には使いたい。そこで、アップロード処理の最中だけメモリ上で座標を店舗/作業場所と突き合わせ、"近い/遠い"の判定と大まかな距離帯だけを残して**生の座標は即破棄**する設計にした話。出張作業場所の座標を持つ場合もスタッフ運用限定で顧客・保険会社には一切出さない。「活用と非保存の両立」の具体的な実装判断。
- 想定読者: 位置情報や個人データを扱うプロダクトの開発者・PM、プライバシー配慮の実装例を探しているチーム。
- 状態: 未着手
- メモ: 個人情報・具体的な顧客データは書かない。教訓は「照合はメモリ内で、保存は結果のみ」「距離は帯に丸めて精密な位置を残さない」「基準座標は最小権限」。公開区分＝要確認（プライバシー方針の外部公開文面は代表確認後）。


## 「写真を撮るだけ」を新規開発せずに実装した ― 競合の目玉機能を"既存資産の接続"で最短で作る
- 切り口: 競合が「写真を撮るだけで作業時刻・工程が自動で残る」を売りにしていた。同じ体験をゼロから作るのではなく、自社に既にあった部品（写真の撮影時刻を読む処理・画像から情報を取り出すAI・車検証の読み取り・顧客/車両/担当の自動ひも付け）を"繋ぐ"だけで、手入力を大きく減らす下書き（施工日・作業時間の推定）を最小の変更で足した話。派手な新機能より「既にあるものを繋ぐ」ほうが速くて壊れにくい、という開発判断。撮影時刻を扱うときの落とし穴（タイムゾーンで日付が1日ずれる／壊れた時計や別日の写真を鵜呑みにしない＝AIは事実を作らない）も具体例として書ける。
- 想定読者: 自社プロダクトに機能を後付けする開発者・PM、競合に機能で追いつきたい小規模チーム。
- 状態: 未着手
- メモ: 競合の実名・優劣比較は書かない（公開区分＝要確認）。「既存資産の接続」「撮影時刻の扱いの注意点」「提案止まりで確定は人」という一般化した設計知見に留める。裏付けは RELEASE_LOG / DECISION_LOG 2026-07-27 フェーズ1エントリ。

## 「1円のズレ」と「飛ばない完了通知」を潰す ― コア業務フローを5系統に割って横断バグ監査した話
- 切り口: 予約受付から会計終了までの一本道を「予約/工程/写真・OCR/AI自動化/会計・決済」の5系統に分け、

- 想定読者: 自社の基幹フローの品質に責任を持つ開発者・PM。個別テストは通るのに通しで壊れる、を経験した人。
- 状態: 未着手
- メモ: 具体的な脆弱点の手口・顧客名・金額実データは書かない。「計算単位を揃える」「累計で判定する」

## 壊れた監視 cron を「鳴らし続ける」のをやめる ― 設定ミスは skip、本物の障害だけ通知する
- 切り口: 残高監視 cron が、秘密鍵の些細な形式ミス（`0x` の付け忘れ）で510回超も「失敗」を鳴らし続けていた。
  修正は"リトライを足す"ことではなく「失敗の種類を分ける」こと ― 設定ミスは skip して失敗連鎖に積まず、本物の
  RPC 障害だけ通知する。ついでに直す場所を「呼び出し元」ではなく「共有関数」にして、監視とアンカリング署名の
  両方を一度に直した話。
- 想定読者: 監視/アラートを運用する開発者、cron・バッチの失敗設計に悩む個人〜小規模の運用者。
- 状態: 未着手
- メモ: 教訓は2つ ―（1）アラート疲れは「全部を失敗として鳴らす」設計から生まれる、種類を分ければ止まる。
  （2）バグは症状（呼び出し元）でなく根（共有関数）で直す。※ 秘密鍵の値・ウォレットアドレス・アンカリング基盤の
  具体は書かない（機密）。公開区分は「要確認」。

- 切り口: 画面のエラー表示に "internal_error" のような意味不明な文字列だけが出るバグを1画面分直そうとしたら、

- 状態: 未着手
- メモ: 「バグ修正依頼が来たら、まず同じ関数の他の呼び出し元を全部見る」という開発習慣の効能の実例として使える。

## 「同業者に電話で頼む」をやめる ― 加盟店同士が手数料0で仕事を回す仕組み

- 切り口: 出張整備・専門施工の現場では、遠方案件や専門外の作業を「知り合いの店に電話で頼む」文化が根強い。
  Ledra では加盟店同士の受発注をアプリ内で完結でき、既存取引先への「指名」依頼はプラットフォーム手数料を
  取らず、請求書払い（掛売）で顧客ごとの締め日にまとめて請求書を自動生成・確認後に送付する形にした。
  「見知らぬ相手を仲介するマッチング」と「既に信頼関係のある取引先との継続取引」を分け、後者からは手数料を
  取らないという設計思想（大手の中抜き構造への問題意識）を、実装の分岐（公開案件=手数料あり / 指名=0）と
  合わせて語れる。将来は空き枠の確認・押さえまでアプリで完結し「作業者が電話対応に追われない」現場を目指す。
- 想定読者: 整備・鈑金・コーティング等の工場経営者、多店舗連携を模索する事業者、B2B SaaS を作る開発者。

## 「電話で枠を押さえる」をやめる ― 二重押さえを防ぐ仮押さえの作り方
- 切り口: 取引先に作業を頼むとき「今週空いてる？」の電話が現場を止める。Ledra では取引先の空きをアプリで見て
  枠を仮押さえ→相手が受注承認で本予約、という流れにした。技術的な肝は「二店が同じ最後の1枠を同時に押さえる」
  競合を防ぐこと。素朴な『空き数を数える→入れる』は非原子で競合窓があるため、DB の advisory lock で
  (店舗,日,枠) ごとに直列化し、占有（既存予約＋有効な仮押さえ）を数えてから入れる、を1関数に閉じ込めた
  （社内の会計番号採番で使っていた手法の再利用）。「新機能はまず既存の手法を探して流用する」設計の実例。
- 想定読者: 予約・在庫など"最後の1個"競合を扱うプロダクトの開発者、B2B 連携を作るチーム。
- 状態: 未着手
- メモ: DECISION_LOG.md 2026-07-20「他店の空き確認＋枠押さえ(Phase 2)」が一次材料。特定店舗の空き・取引額・
  個人情報は載せない。プライバシー(誰に空きを見せるか)は「取引先=許可制」に留めた点も語れる。

## 「終日お預かり」をどう予約に落とすか ― 既存の暗黙ルールに逆らわない機能追加
- 切り口: コーティングやPPFのように「朝預けて夕方引き取り」の1日仕事を、時間枠だけの予約システムに
  後付けで載せる話。素直に 00:00〜23:59 の枠として保存する手もあるが、Ledra は元々「時刻が空＝終日」を
  カレンダー同期や店頭表示で暗黙に使っていた。新機能はその既存ルールに揃え、`all_day` フラグ1つで
  「終日という意図」を明示しつつ、競合チェック（ダブルブッキング防止）だけは"当日を丸ごと押さえる"よう
  DB関数を1箇所直す、という最小差分にした。「新機能ほど既存の慣習を調べてから足す」という現場的な設計判断の例。
- 想定読者: 予約・スケジュール系のプロダクトを作る開発者、機能追加で技術的負債を増やしたくないチーム。
- 状態: 未着手
- メモ: DECISION_LOG.md 2026-07-20「予約に終日を追加」が一次材料。特定テナントの数値・個人情報は含めない。

## 「返信は返したのに処理が消える」― サーバーレスの fire-and-forget 落とし穴

- 切り口: LINEの自動応答のように「まず200を即返し、重い処理は裏で続ける」構成は、
  サーバーレス環境だとレスポンス送出後に裏処理が無言で打ち切られることがある。Ledraでは
  予約確定時の会計提案・カレンダー同期が撃ちっぱなし（未await）で走っており、
  Next.jsの `after()` に載せた後も「外側が先に終わると中の未完了処理が捨てられる」問題が残っていた。
  await して完走を保証する形に直した実例。「裏で流しておけば大丈夫」がなぜ危ういかを、
  テストで再現（撃ちっぱなしだと落ちる回帰テスト）まで含めて説明できる。
- 想定読者: 業務システム／SaaSを作る開発者、サーバーレス移行を検討中のチーム。
- 状態: 未着手
- メモ: DECISION_LOG.md 2026-07-18「LINE予約枠確定の背景処理は…after()内でawait完走」エントリが
  一次材料。特定テナントの数値・個人情報は含めない。技術ネタなので事業機密には触れない。
