## 2026-07-17 工程ガイドは「サーバ側の強制ゲート」ではなく「UI側のソフト警告」で実装する

1. 日付: 2026-07-17
2. 起きたこと: 26個の機能アイデアを既存導線と突合し、6つの組み合わせ（バンドル）に整理。
   最推奨のバンドルB「工程ゲート統一」（撮り忘れ防止=7／新人ナビ段階進行=25／チェックリスト=6）
   の第1弾として、工程ごとの写真ガイド／確認チェックリストを実装した。
3. 以前の考え: 当初案では「必須写真が揃うまで工程完了をブロックする」サーバ側ハードゲート
   （`advance` ルートで未達なら遷移拒否）を想定していた。
4. 違和感・問題: (a) `docs/field-workflow-roadmap.md` の設計思想が明確に「強制停止は最小限／
   警告は出すが止めない」と定めている。(b) git履歴に「進行ボタンの完了不能バグ」(commit 83db98d)
   があり、advanceに強い前提ゲートを足すと同種の不具合を再発させるリスクが高い。(c) 現状の
   データモデルでは写真は証明書 (`certificate_images`) 紐付けで、工程単位の写真リンクが存在せず、
   自動「撮り忘れ検知」には新規インフラが必要で差分が大きい。
5. 決めたこと: サーバ側はハードゲートを入れず既存 `advance` の挙動を維持。工程ガイドは
   `workflow_templates.steps[]`（JSONB）に任意フィールド `required_photos`/`checklist` を足し、
   ステッパーUIでガイド表示＋作業者の手動チェック＋未確認時の一度だけのソフト警告として実装。
   判定ロジックは純関数 `stepChecklist.ts` に隔離して単体テスト。
6. 捨てた選択肢: (a) advanceでのサーバ側強制ブロック — 思想違反＋完了不能バグ再発リスク。
   (b) 工程↔写真の自動リンク＋自動検知 — 新規テーブル/アップロード導線が必要で差分過大、
   第1弾の範囲外（将来 `certificate_images` に `step_key` を足す拡張余地として残す）。
7. 判断理由: 「現場に記録作業を増やさない／強制停止は最小限」という確立済みの思想と、
   進行不能バグを起こさない安全性を最優先。マイグレーション不要・後方互換で差分が小さく、
   既存の写真ガイド優先度（ロードマップ最優先項目）に直接効く。
8. まだ答えが出ていないこと: 工程ごとの写真を実際のアップロードと突き合わせて「本当に撮ったか」
   を自動判定する仕組み（工程↔写真リンク）は未実装。JobStatusPanel 側の簡易進行ボタンには
   まだガイドを出していない（第2弾候補）。測定器OCR（アイデア8）で `required_measurements` を
   自動充足する拡張も未着手。
9. 公開区分: 公開可（現場負担軽減の思想・写真ガイド機能はnote発信向き。特定テナントの
   数値・個人情報は含まない）。

## 2026-07-16 現場DX機能(音声/写真/OCR/振り分け)は「新規AIより既存資産の転用」で埋める
1. 日付: 2026-07-16
2. 起きたこと: 「話すだけで作業記録」「写真で点検表」「LINEで見積→承認→支払い」
   「入庫即・自動振り分け」「車検証/伝票/ラベルOCR」の5機能案について、
   現状コードとの差分を全ソース読了ベースで棚卸しした。結果、5機能の土台は
   ほぼ実装済みで、欠落は各機能の「最後の自動化ピース」だけだと判明した
   （音声メモ→証明書ドラフト・車検証/納品書/身分証OCR・LINE会話フロー承認・
   Stripe Text-to-Pay・入庫時ワークフロー提案などが既に稼働）。
3. 以前の考え: 現場DX機能は「新機能」として一から作る前提で語られていた。
4. 違和感・問題: 既存に同型の実装（`identityOcr.ts` の Vision 二段OCR、
   `caseAssignSuggest.ts` の3段振り分け、`workflowAuto.ts` の opt-in 提案保存）が
   あるのに、それを無視して作り直すと重複・不整合・レビューコスト増になる。
   特にLINE決済は既存の「壁3（金額の外向き確定は人）」設計と衝突しうる。
5. 決めたこと: (a) 走行距離/タイヤOCR は `identityOcr.ts` と同型の Vision OCR
   （Sonnet→低信頼のみOpus昇格・DB非永続・フォーム自動入力）として新規実装。
   (b) 整備ジョブの担当メカニック自動提案は `caseAssignSuggest.ts` の3段
   （スキルマッチ→履歴頻度→AI）を `staff_members` 向けに転用し、既存の
   `staff/skills.ts` のスキル辞書を再利用。入庫時に `workflowAuto` と同じ
   fire-and-forgetで提案保存（`reservations.ai_assignee_suggestion`）、割当確定は人。
   いずれも opt-in（既定OFF）・監査可能。(c) LINE見積→承認→支払いは、既存の
   opt-in アクション（`inbound_message.auto_conversation_flow` ＋ 請求書作成 ＋
   `invoice.auto_send_on_confirm` の Stripe リンク送付 ＋ Stripe webhook）の
   合成で成立するため新規コードを足さない。
6. 捨てた選択肢: LINE承認から決済リンクを自動送付する新トリガーの新設 —
   既存の opt-in アクションと重複し、かつ「金額の外向き確定は必ず人（壁3）」に
   触れるため却下。写真からの前後自動分類・車両図ダメージマップは今回の3機能に
   含めず見送り（別スコープ）。
7. 判断理由: Ledra の自動化は全機能が「AIは提案、確定は人・opt-in・監査ログ」で
   統一されており、この不変条件に揃えるのが最小差分かつ最も安全。既存ヘルパの
   再利用で辞書・パターンの二重管理を避けられる。
8. まだ答えが出ていないこと: 提案した担当候補・OCR結果を実画面（案件詳細/点検表
   フォーム）へ差し込むフロントUIは本PRの範囲外で未着手。OCRルートと
   assigneeAuto は実APIキー＋実画像＋実DBを要するためE2E実走は未検証
   （純ロジックは単体テストで担保）。LINE決済の「合成で足りる」判断が現場の
   実オペレーションで十分かは【要確認】。
9. 公開区分: 公開可（設計方針の技術的意思決定で機密情報を含まない）

## 2026-07-16 LINE Webhookの後続処理は自前の.catch()ではなくNext.jsのafter()で保護する
1. 日付: 2026-07-16
2. 起きたこと: 「LINEの自動返信が返ってこない」との報告を受けて調査したところ、
   `src/app/api/line/webhook/route.ts` が `handleWebhookEvents(...).catch(...)` を
   `await`/`waitUntil`/`after()` のいずれでも保護せず、レスポンス確定前に
   fire-and-forgetで切り離していたことが判明。サーバーレス実行環境では
   レスポンス送信後に処理が打ち切られうるため、AI自動返信やLINE push送信が
   完了前に中断され、例外も表に出ないまま「返信が来ない」症状になっていた。
3. 以前の考え: LINEは200を即座に返す必要があるため、後続処理は
   awaitせず投げっぱなしにする実装で問題ないと考えられていた。
4. 違和感・問題: 「投げっぱなし」が本当に安全なのは、実行環境がレスポンス
   送信後も関数プロセスを（少なくともある程度）生かし続ける場合に限られる。
   Vercelのようなサーバーレス環境ではその前提が保証されない。
5. 決めたこと: `handleWebhookEvents(...)` の呼び出しをNext.js標準の `after()`
   でラップする。あわせて `export const maxDuration = 60` を設定し、
   OCR/LLM呼び出しチェーンが既定の実行時間で打ち切られないようにする
   （60秒は `vehicles/parse-shakken` 等、同様にOCR/LLMを呼ぶ他ルートに合わせた値）。
6. 捨てた選択肢: (a) QStash等の外部キューに完全移行する案 — 変更範囲が大きく、
   今回の不具合修正としては過剰。(b) `waitUntil` を直接使う案 — このリポジトリの
   Next.js 16では `after()` が標準APIとして提供されており、他ルート
   （`src/lib/edge/eventIngestion.ts` 等）で既に使われている確立済みパターンの
   ため、それに揃えた。
7. 判断理由: 既存コードベースの確立済みパターンに合わせることで、
   レビューコストと将来の一貫性を優先した。
8. まだ答えが出ていないこと: `src/lib/ai/automation/conversationFlowPostback.ts`
   の `handleSlotSelected` 内に、同じクラスの未awaitのfire-and-forget呼び出し
   （会計カテゴリ自動分類・ワークフロー自動提案・Googleカレンダー同期）が
   複数残っており、今回のPRでは対応していない（別途対応要否を判断中、
   OPEN_QUESTIONS.md参照）。また、「自動返信が来ない」という報告のうち、
   どこまでが今回のバグ由来でどこまでがテナントのopt-in設定OFFによるものかは
   【要確認】（対象テナントのAI自動化設定を未確認）。
9. 公開区分: 公開可（実装パターンの技術的な意思決定で機密情報を含まない）

## 2026-07-15 点検写真は証明書経路を流用せず軽量アップロードで Storage 化する
1. 日付: 2026-07-15
2. 起きたこと: 点検フォームの写真を base64 のまま JSONB に保存していた問題を解消するにあたり、
   既存の証明書写真アップロード経路 (`/api/certificates/images/upload`) を流用できるか検討した。
3. 以前の考え: 写真アップロードは証明書経路が唯一の実装なので、それを再利用すればよいと考えていた。
4. 違和感・問題: 証明書経路は certificates テーブルに密結合で、TSA/C2PA/Polygonアンカー等の
   重い証跡パイプラインを伴う。点検は法的証拠レベルを要さないため、流用すると過剰かつ密結合になる。
5. 決めたこと: 点検用に軽量な専用ルート `/api/admin/inspection-records/images` を新設し、
   共有 `assets` バケットへ GPS/EXIF 除去のうえ保存して公開URLを返すだけにする
   （部品エビデンス `stageInstallationPhoto` と同じ最小構成）。`photo_urls` は既に JSONB 文字列配列の
   ためマイグレーション不要。
6. 捨てた選択肢: (a) 証明書経路の流用（密結合・過剰）、(b) `processUploadedPhoto`/`uploadHandler` を
   レコード種別非依存に汎用リファクタ（差分が大きく、点検の要件に対して過剰投資）。
7. 判断理由: 「効くところにだけ最小の追加」。点検に必要なのは Storage 保存とプライバシー保護
   (GPS除去) のみで、証跡は不要。既存の軽量アップロード先例を踏襲すれば小差分で完結する。
8. まだ答えが出ていないこと: 点検写真をオフライン (outbox) 対応にするかは未対応（証明書は対応済み）。
   現状はオンライン前提。需要が出たら証明書と同じ outbox 経路に載せる余地あり。
9. 公開区分: 公開可（一般的なアーキテクチャ判断、機密性なし）。

## 2026-07-15 膜厚OCRは NexPTG 正規化スキーマではなくフォーム行形状で返し、値は編集下書きにする
1. 日付: 2026-07-15
2. 起きたこと: 膜厚の手打ちを減らす写真OCRを実装するにあたり、出力形状を
   既存の NexPTG 同期 (`thickness_measurements` テーブルの place_id/section/value_um) に合わせるか、
   証明書フォームの行形状 (`{location, before_um, after_um, notes}`) にするか検討した。
3. 以前の考え: 膜厚データは NexPTG 正規化スキーマが正なので、それに合わせるべきかと考えた。
4. 違和感・問題: NexPTG は単一 value_um の測定点列で「施工前/後」の概念が無く、別テーブルに保存する
   デバイス同期経路。証明書フォームは施工前後μmをインライン JSON に持つ別モデルで、両者は用途が異なる。
5. 決めたこと: OCR はフォーム行形状で返し、`FilmThicknessSection` の編集可能な行に追記する。
   部位名は保守的な純関数 `mapPanelToPreset` で標準13部位へ寄せ、確証が無ければ元の文字列を残す。
   AI は強制せず修正候補を出すだけ（`docs/field-workflow-roadmap.md` のガード遵守）。
6. 捨てた選択肢: NexPTG スキーマへの正規化（用途違い・別保存経路で不整合）、
   OCR結果を確定値として自動反映（現場ガードに反し、誤読が証明書に直行するリスク）。
7. 判断理由: OCR の出力先はフォームなので、そのフォームの真実 (film_thickness_json) に直結する形状が
   最小差分で自然。精度は Sonnet 固定＋低confidenceで Opus 昇格 (identityOcr 踏襲) とし、
   最終確定は人に委ねる。
8. まだ答えが出ていないこと: 実機の膜厚計表示・手書きシートでの読み取り精度は実写真での検証が未実施
   （【要確認】現場サンプルでの精度）。
9. 公開区分: 公開可（設計判断。ただし精度の定量値は未検証のため対外的な数値主張はしない）。

## 2026-07-14 マイグレーションの CHECK 制約は NOT VALID + VALIDATE で追加する
1. 日付: 2026-07-14（コミット `0e49489` の日付。`git log` で確認）
2. 起きたこと: CHECK 制約をそのまま追加するマイグレーションが、既存行の一括検証で
   ロックを長時間化させ本番マイグレーションを詰まらせるリスクを持っていた。
3. 以前の考え: CHECK 制約は `ALTER TABLE ... ADD CONSTRAINT` で直接（検証込みで）
   追加していた。
4. 違和感・問題: テーブルが大きい場合、制約追加時の一括検証スキャンでロック時間が
   延び、本番デプロイのリスクになる。
5. 決めたこと: 制約追加は `NOT VALID` で入れ、別ステートメントの
   `VALIDATE CONSTRAINT` で検証する2段階方式に統一。
6. 捨てた選択肢: 従来通り `ADD CONSTRAINT` を1ステートメントで直接実行する方式。
7. 判断理由: ロック時間を短く保ちながら、最終的に制約の妥当性は保証できるため。
8. まだ答えが出ていないこと: 既存の過去マイグレーションへの遡及適用は未実施
   （【要確認】対象範囲の棚卸し）。
9. 公開区分: 公開可（一般的な Postgres 運用プラクティス、機密性なし）
