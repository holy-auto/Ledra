## 既存の決定（このログ作成時点で把握できているもの）

## 2026-07 マイグレーションの CHECK 制約は NOT VALID + VALIDATE で追加する
- 背景: CHECK 制約をそのまま追加すると既存行の一括検証でロックが長時間化し、
  本番マイグレーションが詰まるリスクがある（コミット `0e49489`）。
- 決定: 制約追加は `NOT VALID` で入れ、別ステートメントの `VALIDATE CONSTRAINT`
  で検証する2段階方式に統一。
- 理由: ロック時間を短く保ちながら、最終的に制約の妥当性は保証できるため。
- 影響: 今後のマイグレーション作成時のデフォルト作法。`docs/dx-tooling.md` 等の
  マイグレーション運用ドキュメントと整合させること。

## 2026年（時期未特定） 完了サインオフの順序ゲート判定は純関数に集約する
- 背景: 「完了報告 → 証明書発行 → 顧客サイン → お会計 → オンチェーン」の
  ワークフローで、順序ゲート・SLA・写真充足判定のロジックが画面側に散らばると
  業種ごとの分岐が発散する。
- 決定: 判定ロジックを `src/lib/signoff/state.ts` の `computeSignoffState` に
  一本化する（README.md に明記）。
- 理由: 案件画面 (`/admin/jobs/[id]`) など複数箇所から同じ判定を参照する必要が
  あり、重複実装を避けるため。
- 影響: サインオフ関連の分岐を増やす際は必ずこの関数を経由すること。
