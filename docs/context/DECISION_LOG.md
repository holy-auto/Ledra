## 2026-07-20 本番マイグレーション停止を復旧: 孤立した旧 certificate_versions を是正しdb pushの詰まりを解消
1. 日付: 2026-07-20
2. 起きたこと: 終日予約(#784)マージ後に本番自動適用(GitHub Actions `db-migrate`)が失敗していることに気づき調査。
   直近3回(#781・#783・#784 のマージ)の `supabase db push` が全て同じ箇所で停止していた。本番DB
   (`cahybswpduchptvyvdkk` / WEB施工証明書)を read-only 調査した結果、`20260719000001_certificate_versions.sql`
   が「`certificate_versions` はあるが `tenant_id` 列が無い → tenant_id インデックス作成で失敗」していた。
3. 以前の考え: 「マージ＝本番適用」は #779 で自動化済みで、以後は放っておいても未適用分が順に当たる想定だった。
4. 違和感・問題: 本番には**旧スキーマの孤立テーブル** `certificate_versions(id, certificate_id, version,
   snapshot_json, created_at)` が存在(0行・アプリ未参照。現行コードは新スキーマ content/content_hash を使用)。
   一方 #781 の新マイグレーションは `create table if not exists` のため「存在するのでスキップ」し、直後の
   `tenant_id` インデックスで落ちる。`db push` は最初のエラーで停止するため、#781 以降の全未適用分(#783 の4本＋
   終日予約 `20260720000004`)がまとめてブロックされ、**コードは本番に出ているのにDB列が無い**状態になっていた。
5. 決めたこと: `20260719000001_certificate_versions.sql` に「本番ドリフト是正」ブロックを前置。tenant_id を欠く
   `certificate_versions` が存在する場合のみ、**0行であることを確認して** `drop table ... cascade` → 正しい新
   スキーマで作り直す(データがあれば `raise exception` で中断＝データ損失防止)。あわせて `create policy` を
   `drop policy if exists` 前置で再実行可能にした。本番で `begin; …; rollback;` のドライランで適用成功を確認後、
   **実際に本番へ適用**した(下記「実施」参照)。
   実施(2026-07-20): 終日予約コードが本番にデプロイ済みなのに `all_day` 列が無く「予約保存が全滅」する本番障害
   が判明したため、詰まっていた6本(20260719000001 certificate_versions 是正 → #783 の4本 → 20260720000004
   reservations_all_day)を Supabase MCP で**本番に直接適用**し、それぞれ正規の version で `schema_migrations` に
   記録(以後の db-migrate はスキップ)。旧 certificate_versions(0行)は破棄し新スキーマ11列で再作成、#783 の
   CONCURRENTLY 索引2本は小テーブルのため非 CONCURRENTLY で同一の最終形を作成(重複 invoice が無いことを事前確認)。
   適用後、終日/時間枠の予約 INSERT→読み戻し・overlap RPC をロールバック付きで実測し保存復旧を確認。
6. 捨てた選択肢: (a) 旧テーブルを手で本番から DROP して DB を直接いじる — 監査に残らず再現性が無い。マイグレーション
   として残す方が正しい。(b) `20260719000001` より前(早いタイムスタンプ)に是正マイグレーションを差し込む —
   `20260719000000` は既に適用済みで隙間が無く、`db push` は 000001 で止まるため後続の新規ファイルは到達しない。
   よって是正は 000001 自身に入れるしかない。(c) ALTER で旧テーブルに欠損列を継ぎ足す — content/content_hash/
   tenant_id/制約/トリガ/RLS を全て手当てする必要があり差分が大きく壊れやすい。0行なので作り直しが最小・安全。
7. 判断理由: 原因は「本番だけに存在する未管理の孤立テーブル」というスキーマドリフト。空で未参照なので破棄が最も
   安全・最小。ガード(存在時のみ・0行時のみ・データあれば中断)で他環境(新スキーマ済み/テーブル無し)でも無害な
   冪等操作になる。ドライラン＋本番直接適用で検証済み。
8. まだ答えが出ていないこと: 旧 `certificate_versions(snapshot_json)` がいつ・どの経路で本番に作られたか(手動/
   削除済みマイグレーション)は未特定。→ 後続6本は本番へ直接適用済みで全て `schema_migrations` に記録・確認済みの

   参照するコードとマイグレーションは同一PRでも本番適用の成否まで確認すべき(今回コードがDB先行で本番障害化)。
   本PRの migration 修正は本番と同一だが、リポジトリ整合のためマージ(既に prod へ 20260719000001 記録済みのため

9. 公開区分: 要確認(技術的な事後対応。テナント固有データ・接続情報は載せない前提で公開可の範囲だが、インシデント

## 2026-07-21 Googleカレンダー同期に定期実行(cron)を追加。push はイベント駆動のまま、pull を定期化
1. 日付: 2026-07-21
2. 起きたこと: 「カレンダー同期は定期的にできてる?」と質問。調査した結果、gcal 同期は push(予約作成/更新/削除時に
   イベント駆動でGCalへ)＋ pull/一括同期は管理画面の手動ボタン(`/api/admin/gcal`)のみで、**定期実行(cron)が無い**
   ことが判明。本番実績も直近同期が11日前、有効テナント2/12・エラー0(＝壊れてはいないが定期的に回る仕組みが無い)。
3. 以前の考え: 予約変更時の push が飛べば十分、という想定だった。
4. 違和感・問題: (a) GCal 側でスタッフが直接動かした予定は、手動 pull しない限り Ledra に取り込まれない。
   (b) push もイベント駆動のため、直近まで続いた予約保存障害(all_day 列欠落)の間は insert 失敗＝push も飛ばず、
   取りこぼしが出ていた。定期的に差分を均す仕組みが無いと乖離が蓄積する。
5. 決めたこと: 新 cron `/api/cron/gcal-sync` を追加。有効テナント(gcal_sync_enabled かつ refresh token あり)を対象に、
   JST「7日前〜60日先」の窓で push＋pull を双方向実行し `gcal_last_synced_at` を更新。`vercel.json` に 15分毎で登録。
   個別テナント失敗は他に波及させず(ベストエフォート)、55秒タイムアウトガードで残りは次回に回す。同期期間の算出は
   純関数 `computeSyncWindow` に切り出しユニットテスト。既存の `pushReservationsToCalendar`/`pullEventsFromCalendar`/
   `verifyCronRequest`/`recordCronSuccess` を再利用(新規ロジックは最小)。
6. 捨てた選択肢: (a) Google Push 通知(webhook/watch)で即時 pull — チャンネル更新管理・再購読・検証が必要で重い。
   まず定期ポーリングで十分。(b) イベント駆動のみ継続 — GCal 発の変更を取り込めず片方向のまま。(c) 1分毎など高頻度 —
   カレンダー変更はそこまで即時性不要でAPIコール増。15分毎で responsive とコストのバランス。
7. 判断理由: 既存の手動同期関数をそのまま定期化するのが最小差分で確実。双方向にすることで GCal 発の変更も取り込め、
   push の取りこぼしも定期 pull で自己修復される。
8. まだ答えが出ていないこと: `gcal_calendar_id` 未設定の有効テナント(1件)は 'primary' にフォールバックするが意図通りか
   要確認。将来 push 通知方式に上げるかは別途(現状ポーリングで許容)。Vercel プランの cron 上限に対する余裕は未確認。
9. 公開区分: 公開可（機能仕様のみ。テナント固有データ・接続情報なし）。

## 2026-07-20 予約に「終日（1日お預かり）」を追加。時刻NULL＋all_dayフラグで表現し、終日は当日を丸ごと占有
1. 日付: 2026-07-20
2. 起きたこと: 「終日予約もできる様にして」と依頼。既存の予約は顧客Web予約ページでは必ず時間枠を選ぶ必要があり、
   管理画面では時刻を空欄にできるが「終日」という明示的な選択肢・ラベルが無かった。対象導線を確認し「顧客Web予約と
   管理画面の両方」で終日予約を作成・表示できるようにすることに決定。
3. 以前の考え: 予約は必ず start_time / end_time を持つ時間枠ベース、という前提で UI・空き状況・競合判定が組まれていた。
4. 違和感・問題: (a) 顧客はコーティング等の1日仕事でも時間枠を選ばされる。(b) 管理画面で時刻を空欄にした予約は
   「終日」なのか「時刻未定」なのか区別できず、`check_reservation_overlap` RPC が時刻NULL行を競合判定から除外していた
   ため、その予約が当日を占有しない（＝別予約と衝突検知されない）。(c) 既に gcal・booths・StorefrontReservations は
   「時刻NULL=終日」を前提に扱っており、慣習が分散していた。
5. 決めたこと: reservations に `all_day boolean NOT NULL DEFAULT false` を追加。終日予約は時刻をNULLで保存（既存の
   「NULL=終日」慣習に統一）し、`check_reservation_overlap` を「all_day 行はその日のどの時間帯とも競合」するよう更新。
   空き状況・候補提案は終日予約を「全枠占有」として数える共通純粋関数 `reservationBlocksSlot` に集約。顧客ページは
   時間枠一覧の上に「終日（1日お預かり）」ボタンを出し、その日に既存予約が1件も無い場合のみ提示。管理フォームに
   「終日」チェックボックスを追加。
6. 捨てた選択肢: (a) 終日を 00:00–23:59 の具体時刻で保存 — 既存の gcal「終日イベント」/booths/店頭表示が全て
   「NULL=終日」前提のため慣習に反し、表示側で終日判定が二重化する。フラグ方式なら意図が明示的で表示も一意。
   (b) all_dayフラグを持たず時刻NULLだけで表現 — 「終日」と「時刻未定」を区別できず、競合判定を全面NULL対応に
   広げる必要があり触点が増える。(c) 複数ブース(max_bookings>1)での終日と時間枠の併存許可 — 既存の checkOverlap が
   そもそも「重なれば1件でも拒否」で max_bookings>1 の同時重複を許していない既知の制約に合わせ、終日は当日無予約時のみ
   受付とする保守的仕様に。
