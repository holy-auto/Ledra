## 記入フォーマット

各エントリには必ず次の9項目を記録する（CLAUDE.md の「Ledra 事業ログ運用ルール」参照）。
数字が不明な場合は `【要確認】` と記載し、推測で埋めない。

```
## YYYY-MM-DD 決定タイトル
1. 日付: YYYY-MM-DD
2. 起きたこと: 何が発生してこの決定に至ったか
3. 以前の考え: それまでどう考えていたか / どうしていたか
4. 違和感・問題: 何がうまくいっていなかったか
5. 決めたこと: 何を決めたか
6. 捨てた選択肢: 採らなかった案とその理由
7. 判断理由: 採った案を選んだ理由
8. まだ答えが出ていないこと: 未解決の部分（重ければ OPEN_QUESTIONS.md にも起票）
9. 公開区分: 公開可／要確認／非公開
```

## 2026-07-15 機能ブラッシュアップは業務ドメイン軸の棚卸し＋既存部品再利用を優先する
1. 日付: 2026-07-15（このログへの記録日）
2. 起きたこと: 機能が 295 画面 / 597 API / 27 cron まで拡大し（実測）、「どこを改善すべきか」
   の全体像が掴みにくくなった。全機能を4等分で棚卸しし、現場負担減・利便性向上に効く
   ブラッシュアップ候補を洗い出した（`docs/feature-audit-brushup-2026-07.md`）。
3. 以前の考え: 改善は個別の要望・不具合ベースで随時対応していた。
4. 違和感・問題: 全体を俯瞰する棚卸しが無いと、既に実装済みの機能を再発明したり、
   最も負担の高い現場フローを見落とす。実際、証明書フォームは音声/AI/Storage写真/
   オフラインまで揃うのに、点検フォームだけ base64 写真・カメラ非直行・AI補助なしで
   取り残されていた。
5. 決めたこと: (a) 棚卸しの切り口は業務ドメイン軸（Q1現場コア/Q2売上経理/Q3取引運営/
   Q4基盤信頼）とする。(b) ブラッシュアップは「既存部品の再利用で小差分」を最優先し、
   イチオシは点検フォーム `InspectionRecordForm` の格上げ（証明書フォームの
   `PhotoUploadSection`/`VoiceMemoPanel` を流用）とする。
6. 捨てた選択肢: ポータル軸での棚卸し（現場負担の観点で提案が分散する）／
   新規機能追加を優先する方針（既存の負担ポイント放置になる）。
7. 判断理由: 現場思想（`docs/field-workflow-roadmap.md`「現場に記録作業を増やさない」）に
   最も直結するのは Q1 の現場入力フローであり、そこに既存資産の再利用で最小差分の
   改善余地が集中していたため。
8. まだ答えが出ていないこと: 実装スコープは未確定（本タスクは棚卸し＋提案書のみ）。
   散文欠落ルート群（`/admin/field-knowledge` 他）の逐条監査は次サイクルに持ち越し。
9. 公開区分: 要確認（機能構成の粒度・規模感が競合に手の内を明かす面がある。
   note化する場合は「現場負担軽減の思想」に抽象化して発信するのが無難）。

## 2026-07-14 マイグレーションの CHECK 制約は NOT VALID + VALIDATE で追加する
1. 日付: 2026-07-14（コミット `0e49489` の日付。`git log` で確認）
2. 起きたこと: CHECK 制約をそのまま追加するマイグレーションが、既存行の一括検証で
   ロックを長時間化させ本番マイグレーションを詰まらせるリスクを持っていた。
3. 以前の考え: CHECK 制約は `ALTER TABLE ... ADD CONSTRAINT` で直接（検証込みで）
   追加していた。
4. 違和感・問題: テーブルが大きい場合、制約追加時の一括検証スキャンでロック時間が
   延び、本番デプロイのリスクになる。
5. 決めたこと: 制約追加は `NOT VALID` で入れ、別ステートメントの
   `VALIDATE CONSTRAINT` で検証する2段階方式に統一。
6. 捨てた選択肢: 従来通り `ADD CONSTRAINT` を1ステートメントで直接実行する方式。
7. 判断理由: ロック時間を短く保ちながら、最終的に制約の妥当性は保証できるため。
8. まだ答えが出ていないこと: 既存の過去マイグレーションへの遡及適用は未実施
   （【要確認】対象範囲の棚卸し）。
9. 公開区分: 公開可（一般的な Postgres 運用プラクティス、機密性なし）

## 2026-07-15（導入時期は【要確認】） 完了サインオフの順序ゲート判定は純関数に集約する
1. 日付: 2026-07-15（このログへの記録日。実装自体の導入日は README.md に記載が
   なく【要確認】）
2. 起きたこと: 「完了報告 → 証明書発行 → 顧客サイン → お会計 → オンチェーン」の
   ワークフローで、順序ゲート・SLA・写真充足判定のロジックが画面側に散らばる
   リスクがあった。
3. 以前の考え: 各画面が個別に順序ゲート・SLA判定ロジックを実装する想定だった。
4. 違和感・問題: 業種ごとの分岐が画面側で発散し、重複実装・不整合のリスクがある。
5. 決めたこと: 判定ロジックを `src/lib/signoff/state.ts` の `computeSignoffState`
   に一本化する（README.md に明記）。
6. 捨てた選択肢: 案件画面 (`/admin/jobs/[id]`) など呼び出し元ごとに判定ロジックを
   個別実装するアプローチ。
7. 判断理由: 複数箇所から同じ判定を参照する必要があり、重複実装を避けるため。
8. まだ答えが出ていないこと: 正確な導入日【要確認】、この関数を経由していない
   画面が残っていないかの棚卸しは未実施。
9. 公開区分: 公開可（アーキテクチャ設計思想は README.md に既に記載済みの公開情報）

## 2026-07-15 事業ログ（docs/context/）の運用ルールを CLAUDE.md に明文化する
1. 日付: 2026-07-15
2. 起きたこと: ユーザーから「重要な実装・意思決定・方針変更が発生したら
   docs/context/ 配下を都度更新せよ」という運用指示を受けた。
3. 以前の考え: docs/context/ は本日新設したばかりで、更新タイミングや
   DECISION_LOG.md の記録項目の運用ルールは未定義だった。
4. 違和感・問題: 更新ルールをチャット上の指示だけに留めると、セッションが
   変わった際に失われ、事業ログが陳腐化するリスクがある。
5. 決めたこと: CLAUDE.md に「Ledra 事業ログ運用ルール」節を追加し、
   (a) 5ファイルそれぞれの更新トリガー、(b) DECISION_LOG.md の9項目記録
   フォーマット、(c) 推測禁止・数字不明時は `【要確認】`、(d) 機密/個人情報は
   NOTE_CANDIDATES.md に転記しない、(e) 作業終了時に事業ログ反映と note候補抽出
   を必須実行、を明文化した。
6. 捨てた選択肢: 運用ルールをチャット指示のみに留め、CLAUDE.md に明文化しない案。
7. 判断理由: CLAUDE.md はリポジトリにチェックインされ以後のセッションでも
   必ず読み込まれるため、都度指示し直す必要がなくなる。
8. まだ答えが出ていないこと: 「重要な」実装・判断の線引き基準（記録対象と
   そうでないものの境界）が未定義（OPEN_QUESTIONS.md に起票）。
9. 公開区分: 非公開（社内の運用ルールであり外部発信不要）
