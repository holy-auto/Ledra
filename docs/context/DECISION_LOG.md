## 記入フォーマット

各エントリには必ず次の9項目を記録する（CLAUDE.md の「Ledra 事業ログ運用ルール」参照）。
数字が不明な場合は `【要確認】` と記載し、推測で埋めない。

```
## YYYY-MM-DD 決定タイトル
1. 日付: YYYY-MM-DD
2. 起きたこと: 何が発生してこの決定に至ったか
3. 以前の考え: それまでどう考えていたか / どうしていたか
4. 違和感・問題: 何がうまくいっていなかったか
5. 決めたこと: 何を決めたか
6. 捨てた選択肢: 採らなかった案とその理由
7. 判断理由: 採った案を選んだ理由
8. まだ答えが出ていないこと: 未解決の部分（重ければ OPEN_QUESTIONS.md にも起票）
9. 公開区分: 公開可／要確認／非公開
```

## 2026-07-14 マイグレーションの CHECK 制約は NOT VALID + VALIDATE で追加する
1. 日付: 2026-07-14（コミット `0e49489` の日付。`git log` で確認）
2. 起きたこと: CHECK 制約をそのまま追加するマイグレーションが、既存行の一括検証で
   ロックを長時間化させ本番マイグレーションを詰まらせるリスクを持っていた。
3. 以前の考え: CHECK 制約は `ALTER TABLE ... ADD CONSTRAINT` で直接（検証込みで）
   追加していた。
4. 違和感・問題: テーブルが大きい場合、制約追加時の一括検証スキャンでロック時間が
   延び、本番デプロイのリスクになる。
5. 決めたこと: 制約追加は `NOT VALID` で入れ、別ステートメントの
   `VALIDATE CONSTRAINT` で検証する2段階方式に統一。
6. 捨てた選択肢: 従来通り `ADD CONSTRAINT` を1ステートメントで直接実行する方式。
7. 判断理由: ロック時間を短く保ちながら、最終的に制約の妥当性は保証できるため。
8. まだ答えが出ていないこと: 既存の過去マイグレーションへの遡及適用は未実施
   （【要確認】対象範囲の棚卸し）。
9. 公開区分: 公開可（一般的な Postgres 運用プラクティス、機密性なし）

## 2026-07-15 事業ログ（docs/context/）の運用ルールを CLAUDE.md に明文化する
1. 日付: 2026-07-15
2. 起きたこと: ユーザーから「重要な実装・意思決定・方針変更が発生したら
   docs/context/ 配下を都度更新せよ」という運用指示を受けた。
3. 以前の考え: docs/context/ は本日新設したばかりで、更新タイミングや
   DECISION_LOG.md の記録項目の運用ルールは未定義だった。
4. 違和感・問題: 更新ルールをチャット上の指示だけに留めると、セッションが
   変わった際に失われ、事業ログが陳腐化するリスクがある。
5. 決めたこと: CLAUDE.md に「Ledra 事業ログ運用ルール」節を追加し、
   (a) 5ファイルそれぞれの更新トリガー、(b) DECISION_LOG.md の9項目記録
   フォーマット、(c) 推測禁止・数字不明時は `【要確認】`、(d) 機密/個人情報は
   NOTE_CANDIDATES.md に転記しない、(e) 作業終了時に事業ログ反映と note候補抽出
   を必須実行、を明文化した。
6. 捨てた選択肢: 運用ルールをチャット指示のみに留め、CLAUDE.md に明文化しない案。
7. 判断理由: CLAUDE.md はリポジトリにチェックインされ以後のセッションでも
   必ず読み込まれるため、都度指示し直す必要がなくなる。
8. まだ答えが出ていないこと: 「重要な」実装・判断の線引き基準（記録対象と
   そうでないものの境界）が未定義（OPEN_QUESTIONS.md に起票）。
9. 公開区分: 非公開（社内の運用ルールであり外部発信不要）

## 2026-07-15 design-sync の guidelinesGlob デフォルトを DESIGN_SYSTEM.md 限定に変更する
1. 日付: 2026-07-15
2. 起きたこと: `src/components/ui/` の UI キットを claude.ai/design（既存の
   「Ledra Design System」プロジェクト）に同期する作業（PR #760）で、同期ツール
   のデフォルト設定 `guidelinesGlob`（`docs/*.md` 等にマッチ）が `docs/` 配下の
   84ファイルを「デザインガイドライン」として一括で拾い上げた。中身を確認した
   ところ、監査レポート・インシデント対応/災害復旧runbook・SSO設定・
   ISO27001/SOC2準備・競合分析・取引先との交渉メモ等、design-agent に渡すべき
   ではない社内機密文書が大量に含まれていた。
3. 以前の考え: `guidelinesGlob` のデフォルト値（`docs/guides/**/*.md`,
   `docs/*.md`, `guides/**/*.md`）はツール側の一般的な既定値であり、そのまま
   使って問題ないと想定していた。
4. 違和感・問題: このリポジトリの `docs/` は「デザインガイドライン専用」では
   なく、経営・セキュリティ・営業戦略を含む全社共通のドキュメント置き場だった。
   デフォルト設定のまま実行すると、機密文書がアップロード前のローカルビルド
   だけでなく claude.ai/design プロジェクトへの実アップロードにまで含まれる
   ところだった（アップロード実行前に発見し、実際のアップロードには含めていない）。
5. 決めたこと: `.design-sync/config.json` の `guidelinesGlob` を
   `"DESIGN_SYSTEM.md"`（リポジトリ内で唯一の実質的なデザインガイドライン
   ファイル）のみに限定した。`.design-sync/NOTES.md` に
   「このオーバーライドを絶対に外さないこと」と明記し、再同期時に既定値へ
   戻らないようにした。
6. 捨てた選択肢: (a) デフォルトの `guidelinesGlob` をそのまま使う案（機密漏洩
   リスクのため却下）、(b) `docs/` 配下を手動で1ファイルずつ機密/非機密に
   仕分けして許可リスト化する案（ファイル数が多く運用コストが高い、かつ新規
   追加ファイルの見落としリスクが残るため却下）。
7. 判断理由: `DESIGN_SYSTEM.md` 単体で必要なデザイントークン・コンポーネント
   一覧という目的を満たしており、それ以外の `docs/` 配下を一切含めない方が
   安全側に倒せるため。
8. まだ答えが出ていないこと: 将来 `docs/` 配下に本当のデザインガイドライン
   文書（ブランドガイド等）が追加された場合の取り込み方針は未定義
   （そのつど `guidelinesGlob` に個別追加する運用を想定するが未確定）。
9. 公開区分: 要確認（同期対象プロジェクトの運用に関わる内容だが、機密文書の
   具体名を含むため社外公開前に精査要）
