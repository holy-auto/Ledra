## 0. この資料の前提（重要な視点の転換）

これまで Ledra の説明は「証明書がブロックチェーンで**改ざんできない**」を前面に出してきた。しかし現場の実態は次のとおり。

- **施工店もお客様も「改ざんされる／された」ことに困っていない。** 紙の証明書を偽造される、書き換えられる、という事故を日常的に経験している人はほとんどいない。
- 改ざん不能は「言われれば確かに安心だが、それが理由で導入したいわけではない」レベルの価値。
- **お客様が納得するのは「作業前後の写真」。** 「ちゃんとやってくれた」と思わせるのは、暗号技術ではなく目で見える施工の証拠（ビフォー／アフター写真）。ここが信頼の実体。
- したがって改ざん防止は **主たる導入理由ではなく、保険会社・中古車流通という"外部の第三者"が関わったときに初めて効いてくる「裏側の保証」** と位置づけるべき。

### 0-1. 改ざん防止が「本当の疑問点」とズレている理由

改ざん防止（ブロックチェーン・アンカリング）が守るのは「**記録された後に書き換えられていないこと**」。しかし現場で実際に問われるのはそこではない。

- **データを入力しているのは店舗自身。** だから疑われるとすれば「店舗が最初から正しい内容を入力したか（＝入力時点の真正性）」であって、「入力後に誰かが書き換えたか」ではない。
- 改ざん防止は **入力後の改変** を防ぐ技術であって、**入力時点の内容が正しいか** は保証できない。つまり「誰も困っていない問題」を守っているに過ぎない。
- では入力時点の信頼はどう担保されるか →  **作業前後の写真がその役割を果たす。** 写真は「実際にこの状態の車に、この施工をした」という入力内容そのものの裏付けになる。お客様も保険会社も、結局はこの写真で納得する。

> つまり訴求の力点は **「改ざんできない」ではなく「作業前後の写真つきで証明書が残る」** に置くべき。改ざん防止は写真という主役を裏で補強する脇役。

この資料では、改ざん防止を「主役」から「縁の下」に下げ、**実際に毎日の業務で何が変わるか／誰がどの場面で何を使うか** を中心に説明する。

> 一言でいうと:
> **「改ざんできないから使う」のではなく、「予約から証明書・請求までを一つの画面でやり切れて、作業前後の写真つきで残り、お客様も後からスマホで見られるから使う」。改ざん防止はそのデータが外（保険・中古車市場）に出たときに勝手に効く保険のようなもの。**

## 1. 既存システムとの違い

### 1-1. 「既存システム」とは具体的に何か

国内のコーティング／PPF／ボディリペア店が今使っているものは、ほぼ次のどれか。

| 今の手段 | 実態 | 何が困るか |
|---|---|---|
| **紙・ノートの台帳** | 施工記録・顧客を手書きで管理 | 探せない／劣化・紛失／再発行できない／集計できない |
| **Excel / スプレッドシート** | 顧客や施工をシートで管理 | 人によって書き方がバラバラ／写真が残せない／証明書にならない |
| **LINE + Google スプレッドシート** | 連絡は LINE、記録はシート | 連絡と記録が分断／お客様に「証明」として渡せない |
| **会計ソフト（freee / マネーフォワード等）** | 請求・会計のみ | 施工内容・写真・予約は対象外 |
| **汎用の整備工場向け SaaS** | 一般整備向け | コーティング/PPF の工程・証明書・保証管理に最適化されていない |
| **kintone 等の業務 DB** | 自社カスタムの台帳 | 証明書・保険連携・お客様への共有が作り込み前提 |

ポイントは、**これらは「社内で記録を残す」ためのもの**であって、**「お客様や第三者に渡せる"証明"を作る」ようには出来ていない**こと。

### 1-2. Ledra が違う3つの軸

#### ① 「記録」ではなく「証明書」が中心にある

- 既存システムの一次データは「顧客」や「請求」や「作業記録」。
- Ledra の一次データは **施工証明書（Certificate）**。
- コーティング/PPF 業界では、**証明書そのものがお客様への価値**（「ちゃんと施工しました」という納品物）。ここを業務の中心に据えているのが Ledra。
- お客様は **QR コード／URL** で、いつでも・何度でも・スマホから自分の証明書を見られる。紙台帳や Excel では絶対にできない。

#### ② 予約 → 来店 → 作業 → 証明書 → 請求 が「1本の線」でつながる

- 既存は、予約は紙、記録は Excel、請求は会計ソフト、と**バラバラ**。同じ顧客情報・車両情報を何度も入力し直す。
- Ledra は `/admin/jobs/[id]`（案件ワークフロー）で、**一つの案件として最初から最後まで引き継ぐ**。
  - 車両ID・顧客IDを次の画面に自動で渡すので **再入力ゼロ**。
  - 重複検知で **二重発行・二重請求を防止**。
  - 飛び込み客もその場で数秒でワークフローに乗る。

#### ③ お店の中だけで完結しない（外とつながる）

ここが既存システムと根本的に違うところ。Ledra は店舗（Admin）の他に **代理店・保険会社・お客様** のポータルを持つ。

- お客様 → 自分の証明書をスマホで閲覧
- 保険会社 → 証明書を検索・照会（書類郵送が不要に）
- 代理店 → 施工店を紹介し、コミッションを管理

既存の Excel・会計ソフト・整備 SaaS は「お店の中で完結」する。Ledra は**お店の外の関係者ともデータでつながる**。これは後から真似しづらい構造的な違い。

### 1-3. 改ざん防止（ブロックチェーン）の正しい位置づけ

- 改ざん防止は **②③の延長線上にある「裏側の保証」**。
- お店やお客様が日常で意識するものではない。
- **「この証明書のデータが、保険会社や中古車市場という"第三者"に渡ったとき、後から書き換えられていないことを技術的に保証できる」** という、**外部に出て初めて意味を持つ**機能。
- ただし注意（§0-1 参照）: 改ざん防止が守るのは「**記録後の改変**」だけ。データを入力するのは店舗自身なので、信頼の実体は **入力時点を裏付ける「作業前後の写真」** にある。改ざん防止は写真の真正性を補強する脇役であって、写真の代わりにはならない。
- だから営業トークでは「改ざんできます/できません」を前面に出さず、まず **「作業前後の写真つきで証明書が残る」** を見せ、その上で「将来お客様の車を売るとき・保険で使うときに、この施工記録がそのまま信用される」という**お客様メリット**に翻訳して話すのがよい。

### 1-4. 既存システムとの違い ひとことまとめ表

| 観点 | 既存（紙・Excel・会計ソフト等） | Ledra |
|---|---|---|
| 中心にあるもの | 記録・請求 | **施工証明書** |
| お客様への共有 | できない（口頭・紙のみ） | **QR / URL でいつでも・何度でも** |
| 予約〜請求 | バラバラのツール | **1本の線でつながる** |
| 写真 | 残しにくい | **証明書に紐づけて保存** |
| 外部連携 | 社内完結 | **保険会社・代理店・中古車市場とつながる** |
| 改ざん防止 | 概念なし | **裏側で自動保証（外に出たとき効く）** |

## 2. 誰が・どんな時に・何を使うのか

Ledra は4種類の利用者がいる。**それぞれ使う場面と画面がはっきり分かれている。**

### 2-1. 一覧（早見表）

| 誰が | どんな時に | 何を使うか |
|---|---|---|
| **施工店スタッフ／オーナー（Admin）** | 毎日の業務（予約・施工・証明書・請求） | 施工店ポータル（PC / iPad） |
| **お客様（Customer）** | 施工後／後日見返したい時 | QR・URL でスマホから証明書ページ |
| **保険会社（Insurer）** | 事故査定・施工実績の確認時 | 保険会社ポータル（証明書検索・照会） |
| **代理店（Agent）** | 施工店を紹介・成果を確認する時 | 代理店ポータル（紹介・コミッション） |

### 2-2. 施工店スタッフ（一番よく使う人）

**いつ:** 朝の確認から夜の締めまで、一日中。
**何を:** 施工店ポータル（`/admin/...`）。PC かカメラ付き iPad。

主な場面と使う機能:

| 場面 | 使う機能 |
|---|---|
| 朝、今日の予定を見る | ダッシュボード／予約管理 |
| お客様が来店 | 顧客登録・車両登録（車検証OCRで自動入力） |
| 作業中 | 写真撮影・アップロード |
| 作業後 | 証明書を作成・発行（QR 自動生成） |
| お渡し | メール送信／QR表示／PDF印刷 |
| 会計 | 請求書作成／POS会計（カード決済） |
| 月末 | 経営分析（売上推移・客単価・リピート率） |

> 毎日使うのは「ダッシュボード・予約・証明書・車両・顧客・請求・設定」の **7つだけ**。残りは必要なお店だけ。

### 2-3. お客様（一番人数が多いが、操作は最小）

**いつ:** 施工が終わった直後、または後日（車を売る時・保険を使う時・メンテ時期）。
**何を:** **アプリのインストールも、ログインも基本不要。** 施工店から渡された **QR コードや URL** をスマホで開くだけ。

お客様ができること:
- 自分の施工証明書を見る（写真・施工内容・保証期間つき）
- 証明書が本物か検証する
- PDF で保存・印刷する
- （テナント別マイページにログインすれば）過去の施工をまとめて見る

> お客様視点では「紙をなくしても、スマホでいつでも見られる」が一番の価値。改ざん防止を意識することはまずない。

### 2-4. 保険会社（外部の第三者）

**いつ:** 事故対応・査定・施工実績の確認が必要な時。
**何を:** 保険会社ポータル（`/insurer/...`）。

- 証明書を検索（証明書番号／顧客名／車両情報）
- 案件として管理（一括操作・テンプレ・自動振り分け・SLA）
- 検索分析・レポート、CSV/PDF出力

> **ここで初めて「改ざんされていない記録」が効く。** 第三者が見るからこそ、データの信頼性が価値になる。

### 2-5. 代理店（紹介パートナー）

**いつ:** 施工店を Ledra に紹介する時・成果を確認する時。
**何を:** 代理店ポータル（`/agent/...`）。

- 紹介リンク発行・トラッキング
- コミッション履歴・明細、ランキング
- キャンペーン・研修コンテンツ、サポート

## 2.6 深掘り：誰が・どんな時に・何を使うのか（施工店 / お客様 / 保険会社）

ここでは特に重要な3者を、**「いつ（きっかけ）→ 何を使う → 何が解決する」** の順で掘り下げる。

### 2.6.1 施工店側（Admin）── 業務の主役

**立場:** 一日中いちばん触る人。Ledra を「店の台帳兼レジ兼証明書発行機」として使う。

#### きっかけ別・利用シーン

| いつ（きっかけ） | 何を使う | 何が解決するか（今までの困りごと） |
|---|---|---|
| 朝、開店時 | ダッシュボードで今日の予約・売上・やることを確認 | 「今日は誰が何時に来る？」を紙の予約帳で探す手間がなくなる |
| 電話/LINEで予約が入る | 予約管理（カレンダー）に登録、Google Calendar 同期 | 予約のダブルブッキング・記入漏れを防ぐ |
| お客様が来店（飛び込み含む） | 来店チェックイン → 顧客・車両登録（**車検証OCR**で自動入力） | 車種・ナンバーの手打ちが消える。飛び込みも数秒で受付 |
| 作業に入る | ワークフロー（受付→作業中→完了）をワンクリック進行 | 「今この車どの工程？」をスタッフ間で共有できる |
| 作業中・前後 | スマホ/iPadで**作業前後の写真を撮影・アップロード** | 後で「ちゃんとやった証拠」になる。クレーム予防・追加提案の根拠に |
| 作業完了 | 証明書を発行（車両・顧客が自動引き継ぎ、QR自動生成） | 再入力ゼロ。証明書がその場で完成 |
| お渡し | メール送信／QR提示／PDF印刷 | 紙が汚れても再発行不要。お客様がスマホで持ち歩ける |
| 会計 | 請求書作成（証明書から金額自動反映）／POS会計 | 二重入力・計算ミスを防止。合算請求も可 |
| 月末・締め | 経営分析（売上推移・客単価・リピート率） | Excel集計が要らない。リピート施策の判断材料に |

#### 施工店にとっての本質的価値

- **「いつもの仕事の順番（受付→作業→お渡し→会計）を変えずに、記録が証明書として自動で残る」。**
- バラバラだったツール（紙の予約帳・Excel・会計ソフト）が**1本の線**でつながり、同じ情報を何度も入力しなくてよい。
- **作業前後の写真**が証明書に紐づくので、クレーム対応・追加提案・リピート訴求すべての武器になる。

> 施工店が一番うれしいのは「改ざん防止」ではなく、**手間が減って、写真つきの証明書が勝手に積み上がること**。

### 2.6.2 お客様側（Customer）── 操作は最小、価値は最大

**立場:** 人数は一番多いが、操作はほぼ「QRを読む」だけ。アプリ不要・ログイン基本不要。

#### きっかけ別・利用シーン

| いつ（きっかけ） | 何を使う | 何が解決するか |
|---|---|---|
| 施工が終わった直後（店頭） | 渡されたQRをその場でスマホで読む | 「ちゃんとやってもらえた」を**作業前後の写真**で実感できる |
| 後日、ふと見返したい時 | 同じQR/URLをもう一度開く | 紙をなくしても何度でも見られる |
| 次のメンテ時期 | 証明書の保証期間・有効条件を確認 | 「保証いつまで？」「次いつ？」が手元で分かる |
| 別の店・知人に見せたい時 | URLを共有 | 口頭説明でなく現物（写真つき証明書）で示せる |
| **車を売る時** | 証明書を提示（中古車店・買取） | 「コーティング済み」を**証拠つき**で主張でき、査定の付加価値になる |
| **保険を使う時** | 証明書を保険会社に参照してもらう | 施工実績がそのまま信用される |
| 過去施工をまとめて見たい | （任意）マイページにログイン | 複数回の施工履歴を一覧できる |

#### お客様にとっての本質的価値

- **「紙をなくしても、スマホでいつでも・何度でも、写真つきで見られる」。** これが紙の証明書との一番わかりやすい違い。
- お客様が納得する根拠は暗号技術ではなく **作業前後の写真**。そこに「いつ・どんな施工をしたか」が添う。
- 将来 **車を売る／保険で使う** 時に、その記録がそのまま価値・信用になる（=お客様メリットとしての"改ざん防止"はここで静かに効く）。

> お客様の負担は「QRを読む」だけ。**意識して使う場面はほぼ無いのに、必要な時に必ずそこにある**のが理想形。

### 2.6.3 保険会社側（Insurer）── 外部の第三者として参照する

**立場:** 普段は使わない。事故対応・査定・施工実績の確認が必要になった時に**証明書を"参照・照会する側"**。

#### きっかけ別・利用シーン

| いつ（きっかけ） | 何を使う | 何が解決するか |
|---|---|---|
| 事故・査定で施工実績を確認したい | 保険会社ポータルで証明書検索（証明書番号／顧客名／車両情報） | 施工店に電話・書類郵送で問い合わせる手間が消える |
| 案件として処理する | 案件管理（一括操作・テンプレ・自動振り分け・SLA） | 問い合わせを案件として滞留なく回せる |
| 内容の真正性を確かめたい | 証明書に紐づく**作業前後の写真**を確認 | 「本当にこの施工をしたか」を写真で判断できる |
| 傾向を把握したい | 検索分析・レポート、CSV/PDFエクスポート | 施工種別×車種×地域の集計を内部資料に使える |

#### 保険会社にとっての本質的価値

- **書類郵送ゼロ・二重入力ゼロ**で、施工実績を即座に照会できる。
- 判断の根拠は、ここでもまず **写真**。コグニセブンが「写真を保険会社に伝送する」のを業界標準にしているのと同じ構図（→ `docs/competitor-cogniseven-broadleaf-2026.md`）。
- **改ざん防止が"初めて意味を持つ"のはこのレイヤー。** 第三者が見る時にこそ「入力後に書き換えられていない」保証が効く。ただし主役はあくまで写真＋標準データで、改ざん防止はそれを裏で補強する脇役。

> 保険会社視点では「**写真つきの施工実績を、郵送なしで・即座に・そのまま信用できる形で参照できる**」ことが価値。

### 2.6.4 3者の比較まとめ

| | 施工店（Admin） | お客様（Customer） | 保険会社（Insurer） |
|---|---|---|---|
| 使う頻度 | 毎日・一日中 | 必要な時だけ（年数回） | 案件発生時のみ |
| 操作量 | 多い（業務全部） | ほぼ無し（QRを読む） | 中（検索・照会） |
| 主目的 | 業務を回す／写真つき証明書を残す | 証明書を受け取る・見返す | 施工実績を参照・確認する |
| 信頼の根拠 | 作業前後の写真 | 作業前後の写真 | 作業前後の写真＋標準データ |
| 改ざん防止の意識 | 普段意識しない | 普段意識しない | **ここで初めて効く（裏側）** |
| 一番の価値 | 手間が減る・証拠が積み上がる | いつでもスマホで見られる | 郵送ゼロで即照会できる |

## 3. 「店舗で行う事」と「お客様が行う事」

役割分担をはっきりさせると、導入時の説明がしやすい。**作業のほとんどは店舗側。お客様は受け取って見るだけ。**

### 3-1. 全体の流れ（誰が何をするか）

```
 ┌─────────────────────── 店舗（Admin）が行う ───────────────────────┐
 予約を受ける → 来店受付 → 顧客・車両を登録 → 施工 → 写真を撮る
   → 証明書を作成・発行 → お客様に渡す（QR/メール/印刷） → 請求・会計
 └────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼  渡す
 ┌──────────────────── お客様（Customer）が行う ────────────────────┐
   QR/URL を開く → 証明書を見る → 必要なら PDF 保存・印刷
   （後日）車を売る時・保険・メンテ時に、また同じ QR から見返す
 └────────────────────────────────────────────────────────────────┘
```

### 3-2. 店舗で行う事（チェックリスト）

| 区分 | 行う事 | 画面 |
|---|---|---|
| 受付 | 予約確認・来店チェックイン | 予約管理 / ワークフロー |
| 登録 | 顧客登録・車両登録（車検証OCR） | 顧客管理 / 車両管理 |
| 施工 | 作業・写真撮影・アップロード | 証明書発行フロー（モバイル可） |
| 発行 | 施工内容・保証条件を入力して証明書を発行 | 証明書 |
| お渡し | メール送信 / QR提示 / PDF印刷 | 証明書詳細 |
| 会計 | 請求書作成・入金管理・カード決済 | 請求・帳票 / POS会計 |
| 管理 | 売上分析・メンバー・店舗設定 | 経営分析 / 設定 |

> 店舗側は「いつもの仕事の順番（受付→作業→お渡し→会計）」のまま。**やり方を大きく変える必要はなく、記録が証明書として自動で残る**のが利点。

### 3-3. お客様が行う事（とてもシンプル）

| 行う事 | 方法 | 備考 |
|---|---|---|
| 証明書を見る | QR をスマホで読む / URL を開く | **アプリ不要・ログイン不要** |
| 本物か確かめる | 公開ページに表示される | 自動で検証される |
| 保存する | PDF出力ボタン | スマホ・PCに保存可 |
| 後で見返す | 同じ QR / URL を再度開く | 紛失しても何度でも |
| （任意）まとめて見る | マイページにログイン | 過去施工を一覧 |

> お客様の負担は「QRを読む」だけ。ここが紙の証明書との一番わかりやすい違い。

### 3-4. 店舗 / お客様 早見対比表

| | 店舗（Admin） | お客様（Customer） |
|---|---|---|
| 使う端末 | PC / iPad | 自分のスマホ |
| 必要なもの | ログインIDとパスワード | QR か URL だけ |
| 操作量 | 多い（業務全部） | ほぼ無し（見るだけ） |
| 主な目的 | 業務を回す・記録を残す | 証明書を受け取る・見返す |
| 改ざん防止の意識 | 普段は意識しない | 普段は意識しない |

## 4. まとめ ── 説明するときの順番

導入の説明やピッチでは、次の順番で話すと相手に刺さりやすい。

1. **今困っていること**から入る（紙・Excelがバラバラ、証明書を渡せない、再発行できない）。
2. **Ledra なら一連の流れが1画面でつながり、お客様もスマホで見られる**（実務メリット）。
3. **誰が・いつ・何を使うか**を具体的に見せる（店舗は業務全部、お客様はQRを読むだけ）。
4. **改ざん防止は最後に、軽く触れる**。「将来お客様が車を売る時や保険で使う時に、この記録がそのまま信用されます」という**お客様メリットの言葉**で。決して主役にしない。

> **改ざんできないこと自体は、今は誰も困っていない。**
> だから売り文句の中心は「業務が楽になる・お客様がいつでも見られる」に置き、改ざん防止は"外に出たとき効く裏側の保証"として静かに添える。これが現場感覚に合った伝え方。
