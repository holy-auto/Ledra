## 1. エグゼクティブサマリ

**結論: Ledra の自動化基盤は既に商用 SaaS として高水準。次の投資は「新しい AI 機能の追加」より
「(a) AI を使わない決定論的自動化の穴埋め、(b) 入力 UI の enum 化 / マスタ選択化、
(c) 既存 auto-actions の有効化率を上げる運用」の 3 点に置くのが費用対効果が最も高い。**

| 層 | 成熟度 | 根拠 |
|---|---|---|
| AI 基盤 | ★★★★★ | 22+ AI ルート / 22 auto-actions 全ライブ配線 / フィールド単位ポリシー / コストキャップ / プラン別モデル / フィードバックループまで完備 |
| コード的自動化 (cron / webhook / outbox) | ★★★★☆ | ロック + 冪等 + リトライ + 失敗トラッカ + 安全網 cron の 5 点セット。残る穴は SLA アラート / 督促 cron / bounce 抑制の 3 つ |
| 入力 UI の簡略化 | ★★★☆☆ | 証明書・車両は OCR / プリセット / AI が充実。**周辺フォーム (保険案件カテゴリ / 担当者名 / BtoB 宛先 / 住所) に自由テキストが残存** |

### 最重要の 5 提案 (先出し)

| # | 提案 | 種別 | 効果 | 工数感 |
|---|---|---|---|---|
| 1 | 保険 SLA 違反の能動アラート cron | コード自動化 | 保険会社契約の信頼性 (SLA が「表示」から「保証」になる) | 小 |
| 2 | 請求書 overdue 自動督促 (opt-in auto-action) | コード + AI | 未回収の回収率向上・毎日の手動確認を排除 | 小〜中 |
| 3 | 保険案件カテゴリの select 化ほか enum 化 8 箇所 | UI 簡略化 | 表記ゆれ根絶 → 後段の自動振り分け / 分析 / AI の精度が構造的に上がる | 小 |
| 4 | 未紐付け膜厚レポートの手動リンク UI | 救済経路 | VIN 不一致時に救済不能な dead-end を解消 | 小 |
| 5 | 担当者名のスタッフマスタ選択化 (3 フォーム共通) | UI 簡略化 | 入力排除 + 担当者別分析 (`/admin/analytics/staff`) のデータ品質向上 | 小 |

**アンチパターン警告**: 本リポジトリは「AI でできること」はほぼやり尽くしている。
ここから AI を追加する場合、**決定論的に解ける問題に LLM を使わない** こと (§3 の各項参照)。
例: SLA 期限判定・督促日判定・郵便番号→住所はルール/API で足り、AI を挟むとコスト・遅延・不確実性だけ増える。

## 2. 現状の成熟度評価 (3 層)

### 2.1 AI 基盤 (実装済みの資産)

- **プロバイダ**: Anthropic 一本 (`src/lib/ai/client.ts`)。プラン別モデル (Starter=Haiku / Standard=Sonnet / Pro=Opus)、
  低確信時の CRITICAL (Opus) 昇格、prompt caching。
- **制御**: フィールド単位 auto/suggest/manual (`fieldCatalog.ts`) + イベント駆動 auto-actions 22 種 (`actionCatalog.ts`、全て opt-in・既定 OFF)。
- **コスト防御**: 月次コストキャップ (`costCap.ts`、超過で自動一時停止) / レート制限 (ai=20req/60s) /
  「ルール一次 → グレーのみ LLM」の 2 段構え (改ざん検知・不正検知・ファジーマッチ・膜厚異常)。
- **信頼性**: `withRetry("anthropic")` + サーキットブレーカ、全ヘルパに決定論的フォールバック、
  `ai_usage_logs` + 運営ダッシュボード + フィードバックループ (`feedbackLoop.ts`) による auto 化推薦。
- **安全**: `promptSafety.ts` (untrusted 入力の境界化)、身分証 OCR のマイナンバー等出力禁止 + `sanitizeOcrResult` フェイルセーフ。

### 2.2 コード的自動化 (cron / webhook / 非同期)

- cron 24 本すべてに `withCronLock` + `sendCronFailureAlert` + `recordCronSuccess/Failure` + 冪等キーがほぼ適用済み。
- webhook は「署名検証 → 冪等 claim (`webhook_processed_events` / `stripe_processed_events`) → 処理 → 失敗時 5xx 再送」の統一パターン。
- **安全網 cron の二重化** (`stripe-event-monitor` / `passport-meta-anchor-retry` / `agent-commissions-reconcile`) が webhook 取りこぼしを自己修復。
- 非同期は「DB outbox (DLQ 付き)」「IndexedDB オフライン outbox (PWA)」「QStash」の 3 層分離。

### 2.3 入力 UI

- **模範例 (再利用元)**: 車検証 OCR (QR 一次 → Vision 補完)、本人確認 OCR (`IdentityScanButton`)、
  メッセージ AI 抽出 (`MessageExtractPanel`)、音声メモ (`VoiceMemoPanel`)、PPF クイックセットボタン、
  車両サイズ SS〜XL ボタン、品目マスタ + datalist 単価自動入力、前回証明書引き継ぎ (`last-cert`)。
- **残存する自由テキスト**: §4 の一覧参照。共通パターンは「マスタが存在するのに text 入力」
  「実質 enum なのに text 入力」「定型文なのに毎回 textarea」の 3 類型。

## 3. 機能領域別 複合チェック

各領域を「現状 → さらに自動化するなら → メリット / デメリット → 推奨」で評価する。
凡例: 🤖=AI 自動化 / ⚙️=コード的自動化 / 🔘=UI 簡略化 / 🏗=バックエンド仕組み化

### 3.1 証明書発行 (`/admin/certificates/new`)

**現状**: OCR・AI 下書き・音声メモ・品質ゲート・auto_draft / auto_create_draft_record (案件完了→draft 起票) まで実装済み。発行 (draft→active) は人。

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| 🔘 担当者名のマスタ選択化 | `mechanic_name` / `installer_name` / 鈑金担当を `/admin/staff` マスタから select | 入力ゼロ化・表記ゆれ根絶・担当者別分析の精度向上 | スタッフ未登録店では一手間増 (自由入力フォールバック併設で回避) |
| 🔘 保証情報 textarea ×3 の定型文化 | warranty_info (整備/鈑金/用品) に「店舗デフォルト保存」ボタン (本体 `warranty_exclusions` に既存の仕組みを横展開) | 毎回の同文入力を排除。既存実装の流用で工数最小 | 定型文の陳腐化リスク (更新導線をセットで) |
| 🤖 備考 (`remarks`) への VoiceMemoPanel 接続 | 既存コンポーネント流用 | 現場で手を汚したまま音声入力できる | ほぼなし (既存機能の配線のみ) |
| 🤖 発行そのものの自動化 (`certificate.auto_issue`) | 完了時に active まで進める | 究極の入力ゼロ | **非推奨**: 証明書は法的証跡でありプロダクトの信頼の源泉。誤発行 1 件のブランド毀損 > 省ける 1 クリック。draft 自動起票 + ワンタップ承認 (承認インボックス `/admin/inbox`) が上限 |

**推奨**: UI 簡略化 3 点のみ。発行自動化は現行の「draft まで自動・発行は人」を維持。

### 3.2 車両・顧客管理

**現状**: 車両登録は OCR + サイズ自動判定 + 名寄せでほぼ最適化済み。顧客は IdentityScan OCR あり。

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| ⚙️ 郵便番号→住所自動補完 | zipcloud 等の無料 API or ローカル辞書。**AI 不要** | OCR 非使用時 (電話受付など) の最大ボトルネック解消。決定論的でコスト 0 | 外部 API 依存 (ローカル辞書なら回避可) |
| ⚙️ 氏名→フリガナ自動候補 | kuroshiro 等のライブラリ or 既存 Haiku 呼び出し | カナ入力の手間削減 | 人名読みは辞書でも誤る → 必ず suggest (確定は人)。漢字人名の読み分けは AI でも不確実 |
| 🔘 年式の近年プリセットボタン | text → 直近 15 年ボタン + その他 | 微小改善 | 優先度低 |

**推奨**: 郵便番号補完は AI を使わない典型例として最優先クラス。フリガナは suggest 止まり。

### 3.3 予約・案件ワークフロー (`/admin/reservations`, `/admin/jobs`)

| 🔘 キャンセル理由の定型ボタン | 顧客都合 / 日程変更 / 店都合 / 重複 / その他 | 理由の構造化 → チャーン分析・ノーショー分析が可能になる | 「その他+自由記述」併設は必須 |

## 4. 表面の簡略化 — 文字入力→ボタン化 候補

3 類型で整理。すべて「自由入力フォールバックを残す」を原則とする (完全排除はイレギュラー業務を殺す)。

### 類型 A: 実質 enum なのに text (即効・工数小)

## 5. バックエンドの仕組み化 — ギャップと提案

調査で特定した「基盤は揃っているのに繋がっていない」5 つの穴。いずれも既存基盤の流用で実装可能。

### 5.1 SLA 違反アラート cron (優先度: 高)

- **現状**: `insurer_sla_config` は GET 時のオンザフライ計算で at_risk/overdue を**表示するだけ**。
- **提案**: cron (毎時) で at_risk/overdue を検知 → `notifications` + メール。エスカレーション先 (管理者) 設定を config に追加。
- **メリット**: SLA が契約上の保証として機能。保険会社向けエンタープライズ営業の実弾。
- **デメリット/留意**: 通知疲れ → 同一案件の再通知は cooldown (既存 `cron_failure_streaks` パターン流用)。

### 5.2 請求書 overdue 自動督促 (優先度: 高)

- **現状**: 期限超過はダッシュボード表示 + 手動 reminder 送信のみ。`follow-up` cron は証明書系のみ。
- **提案**: auto-action `invoice.auto_remind_overdue` (opt-in・既定 OFF) を追加し、`follow-up` cron に督促ステージ (期限+3 日 / +10 日、回数上限) を追加。送付チャネルは `documentAuto.ts` の LINE→メールフォールバックを流用。
- **メリット**: 未回収圧縮。心理的に嫌がられる「督促」こそ自動化の価値が高い業務。
- **デメリット/留意**: 入金済みとの競合 (入金確認遅れで督促が飛ぶ事故) → 送信直前に支払状態を再確認。除外顧客リスト必須。

### 5.3 未紐付け膜厚レポートの手動リンク UI (優先度: 中)

- **現状**: VIN 完全一致のみ。不一致は「車両側に VIN を登録して再同期」以外の救済なし。
- **提案**: 未紐付けタブに手動リンク (車両検索 + VIN 部分一致サジェスト)。リンク操作は監査ログへ。
- **教訓として一般化**: **自動マッチングには必ず手動オーバーライド経路を用意する** (Square 注文の ai-link + link 確定はこの成功例)。

### 5.4 Resend bounce/complaint の自動抑制 (優先度: 中)

- **現状**: webhook でログ記録止まり。バウンス先へ再送し続ける。
- **提案**: bounce/complaint → `email_suppressions` テーブルへ自動登録、全送信前にチェック。顧客詳細に「メール不達」バッジ。
- **メリット**: 送信レピュテーション保護 (ドメイン全体の到達率に効く)・無駄送信の排除。
- **デメリット**: 誤バウンス (一時的な full mailbox) の永久抑制 → soft/hard bounce を区別し soft は N 回で抑制。

### 5.5 決定論化によるAIコスト削減 (優先度: 中・継続)

- **方針**: 「AI 推定 → 人が確定」した結果を**マッピング/辞書として保存し、次回からコード側で解決**する。
  - POS 在庫引落: メニュー↔SKU マッピングテーブル化 (AI は未設定品目のみ)
  - 勘定科目: 品目→科目の確定履歴を辞書化 (`accountingCategoryEstimate` は新規パターンのみ)
  - 顧客ファジーマッチ: 確定した対応を alias として保存
- **メリット**: コスト・遅延・不確実性が同時に下がり、監査可能性が上がる。AI は「初回の教師」に退く。
- **デメリット**: マッピングの陳腐化 → 変更時に無効化する運用フック。

### 5.6 (参考) やらないと判断してよいもの

| 項目 | 理由 |
|---|---|
| Supabase Realtime への移行 | ポーリング + Redis キャッシュ (PR #663/#664) で実用十分。接続管理の複雑性に見合わない |
| 通知の DB トリガ化 | アプリコード一元化は追跡容易性の意図的設計。崩す理由がない |
| ニュース cron への LLM 要約追加 | RSS+キーワードで機能している。要約は nice-to-have でコスト定常増 |

## 6. ガバナンス — 壁3 撤廃後のリスク管理

**事実**: `NEVER_AUTO_FIELDS` / `NEVER_AUTO_ACTIONS` は現在**空** (`fieldCatalog.ts:670`, テスト `recommendedActions.test.ts` が「Wall 3 disabled」を明示)。
ハードコードの禁止リストは撤廃され、制御は「opt-in (既定 OFF) + 推奨プリセット (高リスク除外) + confidence 閾値 + 月次コストキャップ」の 4 層に移行済み。

### この設計のメリット / デメリット

| | 評価 |
|---|---|
| メリット | テナントの成熟度に応じて自動化天井を上げられる (供給チェーン auto-send の「上限額 + 月次上限」モデルが好例)。フィードバックループの推薦と整合 |
| デメリット | 「絶対に自動化されない」というコードレベルの保証が消えた。**設定ミス・悪意ある管理者・UI の誤解**で `certificate.auto_issue` 等を ON にできてしまう |

### 推奨ガードレール (撤廃を維持したまま安全性を回復する 4 点)

1. **高リスクアクションの ON 操作に確認ダイアログ + 監査ログ強化**: 発行/送付/課金系を ON にする操作は
   `ai_settings_changed` 監査 (既存) に加え、オーナー権限限定 + 二段確認 + (Pro 契約では) 書面同意フラグ。
2. **段階解禁 (graduation)**: `feedbackLoop.ts` の `enable_auto` 推薦 (サンプル ≥20 かつ平均確信 ≥0.8) を
   **高リスクアクションの ON の前提条件** にする (実績なしでいきなり auto_issue ON を不可に)。
3. **自動実行の日次上限**: コストキャップ (円) に加え、**件数キャップ** (例: 自動起票は 50 件/日) を追加。
   プロンプトインジェクションや異常入力による大量自動実行の爆発半径を制限。
4. **kill switch の周知**: master switch OFF で全停止できることを設定 UI 最上部に常時表示 (既存機能の可視化のみ)。
