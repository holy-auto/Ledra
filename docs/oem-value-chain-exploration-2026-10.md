# OEM が注目した3点（バリューチェーン・入力の簡略化・データ利活用）をどこまで強くできるか

作成: 2026-10-16（`date -u` で確認）／きっかけ: Japan Mobility Show Bizweek 2026（会期 10/13〜16）で、
トヨタをはじめ複数の OEM と話し、次の3点に関心を持たれた（代表の報告）。

1. バリューチェーンの強化
2. データ入力の簡略化
3. データの利活用の方法

この文書では、3点それぞれについて、**今のコードで何ができていて、どこを足せば OEM に見せられる形になるか**を整理する。
根拠はリポジトリ内のコードと docs。数字には出典を付けた。

---

## 結論

**3点とも強くできる。ただし OEM の前に出すには、順番を守る必要がある。**

- **入力の簡略化**: 小さい改修で効くものが多い。すぐ着手できる。
- **バリューチェーン**: 仕組みはほぼ作ってある。今は公開ゲートで閉じているか、配線が一本抜けている。
- **データ利活用**: 一番の壁はコードではない。次の2つが足りない。
  - **データ量**: 本番の VIN 付き車両が1台、ブロックチェーンのアンカーが0件。
  - **法的な土台**: 規約・プライバシーポリシーに、メーカーへ提供できる根拠が無い。

推奨する順番は次のとおり。

1. 入力を減らして、**VIN 付きの記録を増やす**。
2. その記録を**つなぐ配線**を直す。
3. **法的な土台**を作る。
4. 実データで OEM に**レポート**を見せる。

1 が進まないと 4 は見本（ダミー）のままになる。

## 1. データ入力の簡略化

### 今あるもの

省力化の仕組みは Web の証明書作成画面に集まっている。

- 車検証の二次元コードを読む（足りない項目は OCR で補う）
  - `src/lib/ocr/shakensho.ts`
  - `src/lib/ocr/shakensho-qr.ts`。車台番号・型式も読める（同ファイル 5・255・303 行）
- 音声メモを AI で整形する（Web のみ）
- AI 下書き
- 走行距離・膜厚・納品書の OCR
- 施工パッケージ・テンプレート
- 基幹ソフトからの取り込み API `/api/v1/ingest/*`（Pro のみ）

### 手間が一番残っている箇所と、打ち手

| # | 残っている手間 | 根拠（確認済み） | 打ち手 | 規模感（推定） |
|---|---|---|---|---|
| 1 | 写真を撮っても、作成中のフォームに何も入らない（#1353 で、AI 下書きが添付済みの写真を読むようにした） | AI 下書きは写真を渡していない（`src/app/api/admin/certificates/ai-draft/route.ts:147` が `photoDescriptions: undefined`）。写真からの下書きは、発行**後**に詳細ページへ案として出るだけ | 写真の Vision 解析を下書き API に渡し、施工種別・施工箇所・材料の候補をフォームに入れる。部品は既にある（`photoContentDraft`） | 小〜中 |
| 2 | 前回の証明書から引き継ぐのが2項目だけ | `applyLastCert` が写すのは有効条件と保証除外のみ（`src/app/admin/certificates/new/CertNewFormWrapper.tsx:260-269`） | コーティング剤・施工箇所・メニューも写す。前回値の API は既にコーティング剤を返している | 小 |
| 3 | 車検証が手元に無いと、車両の特定が手入力になる | ナンバー認識・VIN デコード・電子車検証の IC 読み取りは、どれも実装なし | ナンバー撮影から自テナント内の車両を検索する。VIN から車種仕様を引くのは **OEM の協力が要る**（第4節） | 中 |
| 4 | モバイルに Web の省力化機能が載っていない | `apps/mobile/src` に音声・AI 下書き・走行距離 OCR の実装が無い（grep で確認。音声は `docs/context/LEDRA_CURRENT.md:1912` にも「未実装」）。アプリ自体が未公開 | 現場の主な端末なので、1・2 をモバイルにも載せる | 中 |
| 5 | 既存システムからの移行で手入力が残る | CSV 取り込みは車両・顧客だけで、引用符の中のカンマに対応していない（`src/app/api/vehicles/import-csv/route.ts`）。整備管理システム（DMS）向けの専用コネクタは無い | 作業履歴の CSV 取り込みを足す。DMS とは ingest API の接続で済ませる | 小〜中 |

**測れていないもの**: ロードマップの目標「発行時間の中央値3分以内」（`docs/ledra-milestone-roadmap-2026-07.md:351`）は、
計測コードが見つかっていない（推定: 未実装。根拠は grep で該当が無いこと）。
OEM に「入力が簡単」と言うなら、**作成画面を開いてから発行するまでの時間**を記録するのが先。数字が無いと主張にならない。

## 2. バリューチェーンの強化

Ledra が埋めているのは、車の一生のうち**ディーラー以外で行われる作業**（施工・整備・鈑金・用品取付）の記録。
OEM・ディーラーから見えない区間にあたる（`docs/toyota-partnership-proposal.md:65-79` のライフサイクル図）。
「強化」とは、この区間の記録を**前後の工程（ディーラー・中古車・保険・オーナー）へ渡せる状態にすること**と捉える。

### 実装の現状（確認済み）

| つなぎ目 | 状態 | 欠けているもの |
|---|---|---|
| 施工店 → 自社の基幹システム（Webhook） | 実装済み。トピックは8種 | **証明書発行（`certificate.issued`）だけ、登録されているのに発火していなかった**（#1353 で発火させた）。作業履歴（`work_history.created`）は基幹ソフトからの取り込み（`src/lib/api/ingest.ts`）で発火している。初版では「2種が未発火」と書いたが、取り込み側がトピック名を組み立てて送っていたのを grep で見落としていた（MISTAKE_LEDGER `M-20261016-grepped-topic-literal-missed-built-topic-names`） |
| 施工店 → 車両単位の履歴（車両パスポート） | 実装済み・**公開ゲートで閉鎖中**（`PASSPORT_PUBLIC_ENABLED` と特許出願前のロック `PASSPORT_PATENT_HOLD`、`src/lib/passport/featureGate.ts`） | 載る項目が、証明書の種別・日付・店名・tx だけ。走行距離・部品装着（GTIN・ロット・シリアル）・傷の位置は載らない |
| 施工店 → 中古車（/market） | 業者間の在庫・商談は実装済み | `market_vehicles.chassis_number` はあるのに、パスポートとつながっていない |
| 施工店 → 保険会社（/insurer） | 本番稼働 | 実契約の保険会社は無い |
| 外部 → Ledra の読み取り API | **無い**。読み取りのスコープ（`certificates:read` など）は定義だけで、使うルートが無い（`src/lib/api-key-scopes.ts`） | OEM・ディーラーが仕組みとして読む手段が無い |
| 施工店 → 材料メーカー（メーカーポータル） | 本番稼働。対象は自社テンプレートで発行された証明書 | 車両の**メーカー（車種）単位**での集計は無い |

### 打ち手（小さい順）

1. **`certificate.issued` を発火させる**（#1353 で実装）
   - 発行の副作用をまとめる `triggerCertificateIssued` に1か所足し、発行の入口4本すべてに効かせた。
   - 効果: ディーラー・整備システムに「この車にこの施工が入った」が届く。OEM の言う「バリューチェーン」に一番直結する。
   - 規模感: 小（推定）
2. **/market の車台番号をパスポートにつなぐ**
   - 中古車の商談画面で施工履歴が見えるようにする。
   - 効果: 残価・下取りの説明材料になる。
3. **パスポートに載せる項目を増やす**
   - 部品装着（`part_installations`）と走行距離を載せる。
   - 効果: OEM から見て、保証・リコールの判断に使える情報になる。
4. **読み取り API を作る**
   - スコープを定義どおりに実装し、OpenAPI を出す。
   - 外部連携の前提になる。
5. **パスポートの公開ゲートを開ける**
   - 特許出願の進み具合（`docs/patents/`）で決まる。代表判断。

### OEM に効きそうな切り口（仮説）

**推定: ディーラー外で行われた ADAS 関連の作業の記録は、OEM にとって価値が高い。**

- 例: フロントガラス交換、バンパー修理、センサー周りへの PPF・ラッピング。これらは運転支援システムの再調整（エーミング）を要することがある。
- 根拠: 実証テストの施工店プロフィールには、既に「ADAS設備」の項目がある（`src/types/manufacturer.ts:383`）。
- 未検証: OEM が実際にこの情報を欲しがっているかは確かめていない。次の面談で聞く項目にする（第5節）。

## 3. データの利活用

### OEM に今すぐ出せるもの

- 材料メーカー向けの証明書 CSV と品質フラグ
  - 自社テンプレート分に限る。上限5000行、顧客名はマスク（`src/app/api/manufacturer/certificates/export/route.ts`）
- 自動車メーカー向けのレポートは**見本だけ**
  - `/manufacturer/report-samples`。数値はすべてダミーで、実データの集計は未実装（`docs/context/LEDRA_CURRENT.md` 2026-10-11 追記）

### 出すのに足りないもの（重い順）

1. **データ量**
   - 本番のアンカー: 0件（2026-10-07）
   - VIN 付き車両: 実測1台（登録24台中、2026-08 時点）
   - 店舗数: 12（目標30）
   - 出典は `docs/context/LEDRA_CURRENT.md` の該当追記。車種別の集計を見せても、統計として意味を持たない。
   - 補足: 車検証の二次元コードからは車台番号が取れる。それでも VIN 付きが1台しか無いので、**どこで抜けているか**を先に調べる。
     推定: 車検証を読まずに手入力で登録された車両が多い。未検証。
2. **法的な土台**
   - 公開中のプライバシーポリシーには、統計・匿名加工データを第三者へ提供する記述が無い（`src/lib/legal/documents.json` に「統計」「匿名加工」の語が無いことを確認）。
   - DPA の処理目的は「サービス改善のための統計分析」まで（`docs/dpa-template.md:37`）。メーカーへの提供は含まない。
   - 自動車メーカー向けは、施工店と車両所有者の同意・契約が先に要ると、社内でも記録済み（`docs/context/OPEN_QUESTIONS.md:37`）。
3. **メーカー（車種）単位の横断集計**
   - 車検証から型式は読めている（`shakensho-qr.ts:303`）。しかし、テナントをまたいで車種別に集める仕組みは無い。
4. **実証テストの案件に車両がつながっていない**
   - `ft_jobs` に車両の列が無いので、不具合を車種・年式で分析できない（`docs/context/OPEN_QUESTIONS.md:38`）。

### 利活用のシナリオ候補（どれも仮説。OEM に確かめる）

| シナリオ | OEM 側の得 | Ledra 側に要るもの |
|---|---|---|
| 車種・色・年式ごとの施工・鈑金の傾向（飛び石・塗装・コーティング不具合） | 品質のフィードバック | 第3節の 1・3、匿名加工の規約 |
| 認定中古車・下取り査定に施工履歴を付ける | 残価の説明材料 | パスポート公開、/market 連携 |
| ディーラー外の ADAS 関連作業の把握 | 保証・安全の判断 | 作業種別の正規化、Webhook |
| 保険（事故時の施工店マッチング・不正検知） | 間接的（系列の損保） | 保険会社との実契約 |

## 4. OEM と組むと一気に楽になる点（交換条件の仮説）

入力の簡略化とデータ利活用は、OEM と**データを交換する**形にすると両方進む。

- **OEM から受け取るもの**: VIN を入れると車種・グレード・色・装備が返る仕様データ。
  - 施工店は VIN を読むだけで、車両情報の入力がほぼ要らなくなる（第1節の 3 が解ける）。
- **OEM へ返すもの**: その車両に入ったディーラー外の作業の記録。
  - 所有者・施工店の同意を取った範囲だけ。匿名加工・集計で返す。

仮定: OEM がアフターマーケット事業者に仕様データを出す枠組みがある、または作れる。
誤っていた場合、VIN デコードは自前（車台番号の規則から車名程度まで）に縮み、入力削減の効果は小さくなる。

## 5. 次の OEM 面談で確かめること

関心を持たれた3点は、言葉が広い。次の面談で、どの意味だったかを絞る。

1. 「バリューチェーン」で一番つなぎたい区間はどこか。
   - 候補: ディーラーの入庫維持、認定中古車、保証・リコール、保険。
2. 欲しいデータの粒度はどれか。
   - 候補: 車両1台ずつ、車種別の集計、イベント通知。
   - 受け取り方はどれか: API、CSV、自社の既存システムへの Webhook。
3. 所有者・施工店の同意を誰が取る想定か。
   - 候補: OEM・ディーラー側か、Ledra 側か。
4. VIN から仕様を引くデータを、アフターマーケット向けに出せるか。
5. ディーラー外の ADAS 関連作業（ガラス交換・センサー周りの施工）の記録に価値があるか。
6. PoC をするなら、どの部署が窓口か。
   - 2026-05 の資料は Toyota Blockchain Lab・KINTO・Woven City を入口にしていた（`docs/toyota-partnership-proposal.md:124-198`）。今回話した部署は【要確認】。

## 仮定（まとめ）

- 仮定: OEM の関心は、展示会での会話以上のもの（具体的な部署・予算につながる）である。
  - 誤っていた場合: 第3節の「法的な土台」への投資は急がず、入力の簡略化（既存の施工店にも効く）だけ進めるのが妥当。
- 仮定: main へのマージは本番に自動で出る。
  - 「本番稼働」と書いた機能の利用件数は数えていない。
- 規模感（小・中）は、関連ファイルを読んだうえでの推定で、見積もりではない。
