## 2-5. 既存45件の遡及入力: 結論

**一括バックフィルはしない。**

理由:

1. 施工時点のメーター値は、システム内のどこにも残っていない（走行距離 0 件）。
   復元元が無い以上、入れられる数字は推測でしかない。証明書は証拠なので、
   推測値を入れることは走行距離が空であることより悪い。
2. 既存45件は既に `active` であり、今回の発行時ゲートは **これから発行するもの** にしか
   かからない。放置しても壊れない。
3. 例外的に、店側に当時の作業記録（整備手帳・紙の作業伝票・請求書控え）が残っている案件は、
   編集API (2-2) から入れれば `vehicle_mileage_logs` に積まれる。**判る分だけ入れる**、
   判らないものは空のまま。これが唯一の正しい遡及手段。

**影響**: 走行距離タイムラインは実質「次回入庫から」始まる。1台につき最初の点は次の証明書発行時、
傾き（年間走行距離）が出るのは 2 回目の入庫以降。対象19台のうち何台が再入庫するかは
【要確認】（リピート率の実績が無い）。

**注意点**: 走行距離ゲートは**初回発行 (draft→active) のみ**に掛ける。`void → active` の
再発行にも掛けると、走行距離なしの既存証明書を void した瞬間に二度と戻せなくなる
（編集フォームは void 中は出ないので入力窓口が無い）。その代わり「void を経由すれば
走行距離なしで active に戻せる」抜け道は残る。
