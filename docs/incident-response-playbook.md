# Ledra インシデント対応プレイブック（IR Playbook）

セキュリティインシデント（情報漏えい・不正アクセス・サービス停止・サプライ
チェーン侵害等）の検知から復旧・事後対応までの手順。ISO 27001 A.5.24–5.28 /
SOC 2 CC7.3–7.5 / 個人情報保護法（漏えい報告義務）に対応。

関連: `docs/disaster-recovery.md`（DR/BCP）・`docs/data-retention.md`・
`docs/security-audit-framework.md`・`docs/slo.md`

## 2. 重大度分類（SEV）

| SEV | 定義 | 例 | 初動目標 |
|-----|------|-----|----------|
| SEV1 | PII 大規模漏えい / 認証バイパス / 本番全停止 / 鍵漏えい | service_role key 流出、全テナント PII 流出 | 即時（15 分以内に IC 招集） |
| SEV2 | 単一テナント影響 / 限定的データ露出 / 重要機能停止 | クロステナント IDOR の悪用痕跡 | 1 時間以内 |
| SEV3 | 影響軽微 / 未遂 / 設定不備 | レート制限不備、軽微な情報露出 | 翌営業日 |

## 3. 対応フロー（検知 → 復旧）

### 3.1 検知 / トリアージ
- ソース: Sentry アラート、`/api/admin/platform/security-audit`（不審 IP/PII 開示ログ）、cron 障害アラート、Stripe/Square 異常、外部報告。
- 一次トリアージで SEV を仮判定し、SEV1/2 は IC を招集。記録係がタイムライン開始。

### 3.2 封じ込め（Containment）
状況に応じて実施（証跡保全を優先し、可能な限り「無効化」を先に）:
- **鍵/シークレット漏えい**: 該当鍵を即ローテーション（`.secrets-age.json` の手順参照: service_role / Stripe / CRON_SECRET / CUSTOMER_AUTH_PEPPER / SECRET_ENCRYPTION_KEY 等）。原則 Vercel env 更新 → 再デプロイ。ただし以下は**単純差し替え不可**、移行手順が必須:
  - **`SECRET_ENCRYPTION_KEY`**: テナントシークレット（LINE/Square/Webhook）は現行鍵でのみ復号できる AES-GCM 封筒で、`secretBox.ts` に**デュアルキー fallback が無い**。鍵を差し替えるだけだと既存シークレットが復号不能になり連携が全断する。**(1) 旧鍵を保持したまま新鍵を併設 → (2) 旧鍵で全レコードを復号し新鍵で再暗号するバックフィルを実行 → (3) 全件移行を確認後に旧鍵を撤去**、の順で行う（漏えい時は旧鍵での復号が攻撃者にも可能な点を踏まえ、バックフィルを最優先で完了させる）。
  - **`CUSTOMER_AUTH_PEPPER`**: 旧 pepper の verifier を併走させ、移行期間（30 日目安）を設けてから撤去（既存 OTP/セッションの無効化を避ける。`.secrets-age.json` 参照）。
- **不正セッション**: 対象ユーザ/顧客セッションを失効（`customer_sessions` revoke）。必要なら全顧客セッション無効化。
- **悪用エンドポイント**: 該当ルートを feature flag / デプロイで停止、またはレート制限を強化。
- **テナント侵害**: `tenant-action` で該当テナントを一時停止。

### 3.3 根絶 / 復旧（Eradication / Recovery）
- 原因コミットの特定と修正、回帰テスト追加、ステージング検証 → 本番デプロイ。
- データ整合性確認（Supabase PITR / バックアップは `docs/disaster-recovery.md`）。
- 監視を強化して再発がないことを確認後、通常運用へ。

### 3.4 証跡保全
- 関連ログ（Sentry、`audit_logs`、`insurer_access_logs`、`pii_disclosure_logs`、Vercel/Supabase ログ）をエクスポートし保全。改ざん防止のため別ストレージに保存。

## 4. 法令・通知義務

- **個人情報保護法**: 個人データ漏えい等で「個人の権利利益を害するおそれ」がある場合、**個人情報保護委員会への報告（速報: 概ね 3〜5 日以内、確報: 30 日以内）** および本人通知。
- **GDPR**（EU 個人データ該当時）: 認識から **72 時間以内**に監督機関へ通知。`docs/dpa-template.md` の手順。
- **サブプロセッサ連携**: Supabase / Vercel / Stripe 等に起因する場合は各社サポート/セキュリティ窓口へ連絡し、DPA に基づく通知を受領。
- 対外公表・顧客通知の文面は IC 承認後にコミュニケーション担当が発出。

---

## 5. 事後対応（Post-Incident）

- **48〜72 時間以内にポストモーテム**（非難なし）を実施し、タイムライン・根本原因・是正・検知改善を記録。
- 是正項目を監査フレームワークの所見ライフサイクルに登録し、次サイクルで検証してクローズ。
- 必要に応じ `docs/AUDIT_REPORT_YYYYMMDD.md` に反映、IR 手順自体の改善。
