# 自社運用 JPKI — Phase 0 実行チェックリスト

> 作成: 2026-05-27
> ステータス: アクティブ (2026 Q2 中に消化)
> 親ドキュメント: `docs/jpki-self-operated-roadmap.md`

このチェックリストを 1 ヶ月で消化し、Phase 1 (申請 + 技術検証) に入る判断材料を揃える。

---

## ⓪ オーナー / 担当

- [ ] **意思決定オーナー**を決める (代表 or CTO 直下推奨)
- [ ] **個人情報保護管理者**を選任 (兼任可、ただし規程上明記)
- [ ] **技術リード**を 1 名アサイン (Ledra コア開発者から)
- [ ] **外部連携リード**を 1 名アサイン (J-LIS / プラットフォーム事業者対応窓口)

---

## ① J-LIS への一次相談 (Week 1)

- [ ] J-LIS の民間事業者向け窓口に連絡
  - 公式サイト: https://www.j-lis.go.jp/ の「公的個人認証サービス」セクション
  - 想定する利用形態 / 月間検証件数 / 業種 (自動車整備 SaaS) を整理して送る
- [ ] 申請区分の確認:
  - **民間事業者** (プラットフォーム事業者経由) → 中間ステップとして推奨
  - **署名検証者** (直接) → 月 5,000 件超で再検討
- [ ] 必要書類リストの取得 (申請書 / 体制図 / セキュリティ要件適合書 等)
- [ ] 想定スケジュールの提示を依頼 (3〜6 ヶ月の目安が一般的)

**成果物**: J-LIS 担当者の連絡先 + 申請区分の決定 + 必要書類リスト

---

## ② プラットフォーム事業者の選定 (Week 1〜2)

- [ ] 候補 2〜3 社にコンタクト:
  - NTT データ「公的個人認証サービスプラットフォーム」
  - 富士通 / NEC / 凸版印刷
  - その他、現時点で民間向け再販を行っている事業者
- [ ] 各社に NDA → 以下を取得:
  - [ ] 月額 / 検証単価 / 初期費用
  - [ ] SDK / API ドキュメント
  - [ ] SLA (稼働率 / 障害時連絡)
  - [ ] DPA (個人情報の取扱いに関する覚書) ドラフト
  - [ ] 認定 TSA との連携実績
- [ ] 比較表を作成し、選定理由を `docs/jpki-vendor-comparison.md` に記録

**成果物**: 選定結果 (or 上位 2 社まで絞り込み)

---

## ③ 社内体制 / 規程整備 (Week 2〜3)

### プライバシーマーク / ISMS

- [ ] 現状確認: `docs/iso27001-soc2-prep.md` を最新化
- [ ] 未取得の場合:
  - [ ] 取得コンサル候補 2 社と面談
  - [ ] 取得タイムライン (通常 4〜6 ヶ月) と JPKI 申請の並行可否を確認
- [ ] 取得済みの場合:
  - [ ] JPKI 利用に伴う規程改定 (取得項目の追加) を実施

### 社内規程

- [ ] 個人情報保護規程に「JPKI で取得した基本4情報の取扱い」を追記
- [ ] 取得目的の限定 (本人確認 / 電子署名のみ) を明記
- [ ] 保存期間 (法定保存期間 + 業務上必要期間) を確定
- [ ] 第三者提供制限 (損保連携時の同意取得方法) を整理

### 入退室 / アクセス管理

- [ ] Ledra のサーバ環境 (Vercel / Supabase) の物理セキュリティ説明を整理
  - J-LIS は「データセンター」想定の要件が残っている可能性あり
  - クラウド前提で問題ないか Phase 0 中に確認
- [ ] アクセスログの保管期間 / レビュー頻度を文書化

**成果物**: 規程改定ドラフト + 取得 / 維持コスト見積

---

## ④ アーキテクチャ詳細設計 (Week 3)

- [ ] **証明書チェーン検証**の責務分担を決める:
  - 自社 (`src/lib/jpki/verifyCertificate.ts`) で完全実装するか
  - プラットフォーム事業者の API に委譲するか
- [ ] **CRL/OCSP**:
  - [ ] J-LIS が OCSP responder を提供しているか確認
  - [ ] CRL のサイズ (現状) を取得 → キャッシュ戦略を確定 (Upstash Redis)
  - [ ] CRL 取得失敗時の縮退ポリシー (fail-closed) を決定
- [ ] **タイムスタンプ**:
  - [ ] 認定 TSA (アマノ / セイコー) と契約予定数 → 単価確認
  - [ ] 1 署名あたりのコストを Phase 2 試算に反映
- [ ] **モバイル NFC**:
  - [ ] iOS Entitlement (NFC Tag Reader) の申請要件確認
  - [ ] Android で互換性のある主要 5 機種を選定
  - [ ] `react-native-nfc-manager` の JPKI APDU 互換性を実機テスト
- [ ] **Web ⇄ モバイル中継**:
  - [ ] QR → スマホ NFC → Web セッション中継の UX 動線を draw
  - [ ] WebSocket / SSE / ポーリングのどれを採用するか決定

**成果物**: アーキテクチャ図 (mermaid) + 技術選定書

---

## ⑤ コスト最終試算 (Week 4)

- [ ] 候補プラットフォーム事業者から見積を取得し、`docs/jpki-self-operated-roadmap.md §4` を更新
- [ ] プライバシーマーク取得 / 更新コストを反映
- [ ] 内部開発工数を最新化 (Phase 1〜2 通算 3 人月想定の妥当性確認)
- [ ] **3 年合計 TCO** を出して TRUSTDOCK と再比較
  - 月間件数別 (100 / 500 / 1,000 / 3,000)
  - 損益分岐ラインの更新

**成果物**: 経営判断用 1 ページ TCO サマリ

---

## ⑥ Phase 1 Go/NoGo 判定 (Week 4 末)

以下を満たせば Phase 1 に進む:

- [ ] J-LIS 一次相談で「民間事業者として申請可能」の感触
- [ ] プラットフォーム事業者を 1 社決定
- [ ] プライバシーマーク取得済 (or 並行取得開始済)
- [ ] 内部規程改定ドラフトが完成
- [ ] 月間想定件数 × 単価 で 2 年目以降の自社 JPKI が TRUSTDOCK より優位
- [ ] 経営承認 (取締役会 or 同等)

判定 NoGo の場合:
- TRUSTDOCK 等 eKYC SaaS 路線へ切り替える
- OCR (Phase 1, 実装済み) のみで運用継続し、月間件数が増えるまで保留
