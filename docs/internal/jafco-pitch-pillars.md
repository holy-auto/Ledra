## 0. 結論（一行サマリ）

> **Ledra は "業務 SaaS の土台" の上に "3 本の証明の柱" が乗った 1 プロダクト**。
> 土台＝統合ワークフロー（予約→作業→請求→入金 / 帳票）と 4 ポータル網。柱＝
> **①施工証明書 × 改ざん検知 / ②部品装着インテグリティ / ③AI 業務自動化**。
> 特に **②部品装着インテグリティ**（三方照合 + 多重署名確定 + 納車時の顧客確認）が、
> 国内に類を見ない差別化。

## 1. 柱の構成（ピッチの背骨）

```
            ┌─ 柱① 施工証明書 × 改ざん検知 ──────────────┐
土台:        ├─ 柱② 部品装着インテグリティ（★目玉）───────┤  → 保険・中古車へ流通
業務SaaS +   └─ 柱③ AI 業務自動化 ───────────────────────┘
4ポータル網
```

| 区分 | 名称 | 一言 | 代表実装 |
|---|---|---|---|
| 土台 | **統合ワークフロー（業務 SaaS）** | 予約→作業→証明書→請求→入金を 1 画面 | `/admin/jobs/[id]`、インボイス帳票 8 種、Square / freee・MF 連携 |
| 土台 | **4 ポータル網** | 業界の価値の流れを 1 つに | 施工店 / 代理店 / 保険会社 / 顧客（+メーカー）5 ポータル + モバイル、保険 case 連携、電子署名 |
| **柱①** | **施工証明書 × 改ざん検知** | 証拠付きの証明書 | Polygon アンカリング + 写真必須ガード + 写真改ざん AI + 4 段階真正性グレード |
| **柱②** | **部品装着インテグリティ** | 偽データ入力と部品すり替えを抑止・検知 | `src/lib/parts/`（三方照合 + OTP 所持証明 + 事業者署名 + RFC3161 TSA + アンカー + 納車時 LINE 確認）|
| **柱③** | **AI 業務自動化** | 面倒な入力は AI が消す | `src/lib/ai/` 44 タスク + `automation/` orchestrator（`photoTamperingAuto` / `fraudScoreAuto` / `thicknessAuto` を `policy.ts` ガード下で自動実行）|

> **繋がり方**: 土台で日々の業務を回す → 柱①②③で「施工した事実・装着した部品」に証拠能力が付く → 4ポータル網で保険・中古車へ流通。**地続きであることが模倣困難性**。

## 2. ★ 柱② 部品装着インテグリティ（このピッチの目玉）

> 「発行時に偽装できるのでは？」への **最終回答**。設計思想からして強い。

**設計思想（正直で、むしろ刺さる）**:
> 物理的な印（シール/刻印）は作業者の手の中にある以上、単体では必ず破られる。だから
> **"物理的に改ざん不能"を目指さない**。代わりに **"複数の独立した関門をすべて欺く必要があり、
> 必ず痕跡か矛盾が残り、割に合わない"** 状態を作る ＝ **抑止 + 検知 + 説明責任**。

**一連の流れ（6 ステップ）**:
```
装着インジェスト → AI 自動検査 → 納品書 OCR との三方照合 → 確定署名 → アンカー → 納車時 顧客確認
（写真/バーコード/  （写真改ざん・  （証明書/請求の部品 = （OTP所持証明      （Polygon）   （顧客が LINE で
  測定値を入口で     使い回し検知）   実物 = 仕入納品書）     + 事業者署名                  本人確認・凍結）
  記録）                            の三者一致を検証）       + RFC3161 TSA）
```

**脅威モデルで語れる（T1〜T7）**: 偽データ入力 / 使い回し / 確定後の書換 / **納車時すり替え（TOCTOU）** /
調達・請求不正 / 数量水増し / **店によるなりすまし確定**。各脅威に対応する関門を持つ。

**特に効く 2 点**:
1. **納車時に "顧客が" 確認する** — 店が支配できない瞬間に第三者（顧客）が検証（出口の封鎖）。
2. **顧客本人の電話 OTP 所持証明 + 電子署名** — 店のなりすまし確定を封じる。連絡先の出所も検証。

**実装ステータス（正直ライン）**: Phase 1〜8 のコードは**実装・本番 DB 適用済み**（`src/lib/parts/` 1,600 行 /
9 API / 監査 UI + 顧客確認 UI `/parts/confirm/[token]` / 84 テスト）。Polygon アンカー・RFC3161 TSA・SMS 配信は
**env 設定で有効化**する段階で、未設定でも安全に degrade（確定フロー自体は止まらない）。

## 3. 5 分プレゼン本編（タイム入り）

> 5 分 ≒ 1,650〜1,800 字。柱②を厚めに。

```
■ 0:00-0:18  Hook
株式会社HOLYの堀越友輔です。私は元々、コーティング・PPF施工店のオーナー。
現場の不便を自分で開発して売っている施工SaaS、それがLedraです。

■ 0:18-0:50  課題（3つの不信）
真面目な店ほど書類で消耗する。さらに保険会社や中古車市場は「本当に施工したのか」
「本当に純正部品を着けたのか」を後から検証できない。偽データの入力、写真の使い回し、
納車前の部品すり替え。"やった事実"が、業界のどこにも信頼できる形で残らないんです。

■ 0:50-1:15  全体像
Ledraは、業務SaaSの土台の上に、3本の"証明の柱"を立てます。土台は予約から入金
までを1画面で回す統合ワークフローと、施工店・保険会社・顧客をつなぐ4つのポータル。
その上に、①施工証明書と改ざん検知、②部品装着インテグリティ、③AI業務自動化。
業務を回すだけで、証拠が貯まり、流通していく構造です。

■ 1:15-1:45  土台（業務SaaS + 網）
まず土台。予約・受付・作業・証明書・請求・入金を1画面で完結し、見積・納品・請求
などインボイス対応の帳票8種もここで出せる。そして保険会社は案件を直接連携、顧客は
自分の車の履歴を持ち、受領は電子署名で完結します。

■ 1:45-2:20  柱① 施工証明書 × 改ざん検知
1本目の柱。発行した証明書は誰にも改ざんできません。写真はAIがPhotoshop痕や
使い回しを弾き、内容はSHA-256でブロックチェーンに刻む。写真の無い証明書は
そもそも発行できない。QRやNFCで誰でも検証でき、5年後10年後も参照され続けます。

■ 2:20-3:15  柱② 部品装着インテグリティ（★目玉）
2本目が、私たちの一番の差別化、部品装着インテグリティです。整備で一番怖いのは
「純正と言って中古や社外品にすり替える」不正。これを物理シールで防ぐのは無理だと
正直に認めた上で、"複数の関門を全部欺かないと不正できない"状態を作りました。
装着を入口で記録し、AIが写真を検査し、証明書・請求の部品と、実際の仕入納品書を
三方で突き合わせる。確定は、顧客本人の電話OTP所持証明と、事業者の電子署名と、
RFC3161のタイムスタンプの三重署名。さらにブロックチェーンに刻み、極めつけは
納車のとき、店ではなく"顧客自身"がLINEで本物だと確認して凍結します。
店が支配できない出口で、第三者が検証する。だから割に合わない。

■ 3:15-3:45  柱③ AI業務自動化
3本目。面倒な入力はAIが消す。車検証QRで車両を一発入力、LINEの予約を自動取込、
音声メモは記録に整形、帳票もAIが下書き。44のAIタスクが動き、写真改ざん検知や
保険不正スコアはポリシーのガード下で自動実行。ただし金額確定・本人確認・証明書の
発行だけは必ず人が承認します。

■ 3:45-4:15  市場 × モート × Why Now
市場は整備・コーティング・板金で5.5兆円、数万社がまだ紙とExcel。3本の柱が
重なると、店舗が増えるほど証拠データが貯まり、AIも改ざん検知も賢くなり、保険・
中古車の参照価値が上がって新店舗を呼ぶ。ここまで作り込んだ事業者は国内にいません。
SDV化と損保の不正対策で、今が10年に一度のタイミングです。

■ 4:15-5:00  トラクション + Ask
これは構想ではなく、490超のAPI、250超のマイグレーション、2千件超のテストで本番
稼働しています。部品装着インテグリティもPhase1から8まで実装済み。今は損保ジャパンを
標的に保険会社の本番接続を狙うフェーズです。シードラウンドの出資をお願いします。
プロダクトはもうある。次はこの柱を"狭く深く"流通ネットワークへ育てる勝負です。
ぜひ続きをお話しさせてください。
```

## 6. 想定質疑（機能柱版で追加）

> 数字・調達・改ざん深掘り（Q13）は `jafco-seed-pitch.md` §6 を併用。

**P1. 機能が多すぎ／総花的では？**
> 1 本の動線です：業務 SaaS で回す → 3 本柱で証拠能力が付く → 網で流通。中古車/BtoB 等の周辺はアドオン化（凍結）済みで、主役は 3 本柱に絞っています。

**P2. 部品装着インテグリティは本当に動くのか？**
> Phase 1〜8 のコードは実装・本番 DB 適用済み（`src/lib/parts/` 1,600 行・9 API・84 テスト・顧客確認 UI まで）。Polygon/TSA/SMS は env 設定で有効化する段階で、未設定でも安全に degrade します。

**P3. それは "発行時の偽装" を本当に防げるのか？**
> 完璧な防止ではなく **抑止 + 検知 + 説明責任** という設計です。脅威モデル（偽データ・使い回し・確定後書換・納車時すり替え・なりすまし確定）の各々に独立した関門を置き、**全部を同時に欺かないと不正できない＝必ず痕跡か矛盾が残る**。決め手は「納車時に顧客自身が確認する」店が支配できない出口です。

**P4. どこから課金？**
> 土台＋柱①③が店舗サブスク。柱②の高額部品の厳格運用と柱①高グレード・保険連携が高単価の保険 ARR。3 階建て ARR（店舗/保険/流通）に対応（`jafco-seed-pitch.md` §4.4）。

> 機能の柱は「広い」と思われがち。**必ず "1 本の動線" として、かつ柱②を主役に語る**。
> 「業務を回すだけで、施工も部品も "やった事実" に証拠が付き、流通する」── これが結論。
