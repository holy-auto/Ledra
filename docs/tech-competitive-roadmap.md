#### ARR ¥10億 到達シナリオ

```
¥10億 = ¥1,000M（年間）

店舗サブスク : 280店 × ¥35,000 × 12 ≈ ¥118M ← ARPU を Standard→Pro で引き上げ
保険会社     : 5社 × ¥5,000〜10,000万/年 ≈ ¥250〜500M ← Lighthouse 本番 + 指定工場ネットワーク
流通 / OEM  : OEM API 従量 + 中古車査定連携 ≈ ¥100M
                                               ─────────────
合算 ARR 到達 : ¥468〜718M（2028 Q2）
ARR ¥10億 到達: 2028 Q3〜Q4（M4 から 1〜2 四半期後）
```

> 店舗数だけでの ARR 10億は到達不可（国内 3,500+ 店が必要）。  
> **保険会社 ARR が 2028 Q2 時点で ARR 全体の 50〜75% を占める構造**になり、  
> 1社目本番が起動すると ARR が階段状に跳ね上がる（Lighthouse 効果）。

#### オンチェーンデータ蓄積の意義

```
       30万件 ─────────────────────────────── M4 (2028 Q2)
       18万件 ─────────────────── M3 (2027末)
        9万件 ─────── M2 (2027 Q2)

↑ この蓄積量が「改ざん不能な施工台帳」としての競合参入障壁を形成する。
  30万件を超えると「Ledra に乗らないと施工履歴が欠落する」
  という保険会社・OEM 側の動機が強くなる（ネットワーク外部性）。
```

### 2.5 フェーズ3の到達地点（2027年末）— 何が完成しているか

フェーズ3（2027 Q3〜Q4）は「スケール準備 & エコシステム拡張」と定義しているが、
**何が達成された状態か**を以下に具体的に示す。

#### 2.5.1 プラットフォーム規模

| 項目 | 数値 | 意味 |
|---|---|---|
| 加盟店舗数 | **~210店舗** | コーティング/PPF/ボディ専業店の国内シェア 2〜3%相当 |
| 累積証明書発行数 | **~20万件**（Phase 3 稼働後 18 ヶ月分 + バックフィル）| 「検証可能な施工記録」の業界最大データベース |
| うちオンチェーン件数 | **~18万件** | 月次マイルストーン表と整合 |

| アクティブ顧客マイページ | **~8万アカウント** | 証明書を「持ち歩く」顧客体験が定着 |

#### 2.5.2 保険エコシステムの状態

フェーズ3終了時点で「保険会社3社が Ledra を業務フローに組み込んだ」状態が実現している。

```
[施工店 (Ledra Admin)]
        │  証明書発行（自動アンカリング）
        ▼
[Polygon Mainnet] ── Merkle root 記録（毎日 03:00 JST）
        │
        ├── [損保ジャパン API] ── 査定システムが自動照会 → 保険金算出自動化
        ├── [保険会社 B API]  ── 証明書有効性チェック → 保険契約審査
        └── [保険会社 C API]  ── SLA モニタリング → 月次レポート自動生成
```

- **保険会社 ARR 規模**: ¥180〜360M/年（3社 × ¥500〜1,000万/月 × 12）
- **API コール量**: 月次 ~50万リクエスト（照会 + Webhook）
- **改ざん検知件数実績**: 蓄積データから不正事案の統計が初めて取れる状態

> **この状態が「外せないインフラ」になるライン**: 保険会社の査定フローに Ledra 証明書照会が組み込まれると、施工店側が「Ledra に登録しない = 保険対応遅延リスク」と認識し始める。ネットワーク外部性が一方向に働く。

### 3.3 オンチェーン記録コスト詳細

> 詳細設計: `docs/anchoring-roadmap.md` §Phase 2/3

#### Polygon ネットワーク前提（2026年現在）

| 指標 | 値 |
|---|---|
| MATIC 価格 | $0.50〜$1.00（試算値）|
| ガス単価 | 30〜100 gwei（Mainnet 平均）|
| `anchorBatch()` ガス消費 | ~50,000 gas（root 書き込み）|
| `anchorCertificate()` ガス消費 | ~45,000 gas（即時書き込み）|

#### バッチ vs 即時の比較

| 方式 | 対象 | tx 数/月 | コスト/証明書 | コスト/月（1,000件）|
|---|---|:---:|:---:|:---:|
| **バッチ（Phase 3 標準）**| 全プラン | ~30 tx | **¥0.01〜0.05** | **¥10〜50** |
| **即時（Enterprise）**| Enterprise のみ | 証明書数 | **¥1〜5** | ¥1,000〜5,000 |
| Phase 1 現行（写真ハッシュ逐次）| 全プラン | 写真枚数 × 3〜5 | **¥0.5〜2** | ¥300〜2,000 |

#### 件数規模別コスト試算（バッチ主体・instant 5%）

| 月間証明書数 | バッチ tx 費 | 即時 tx 費（5%）※ | 合計 Mainnet コスト/月 |
|:---:|:---:|:---:|:---:|
| 1,000件 | ~¥3〜22 | ~¥5〜34（50 tx）| **~¥8〜56** |
| 10,000件 | ~¥3〜22 | ~¥50〜340（500 tx）| **~¥53〜362** |
| 100,000件 | ~¥3〜22 | ~¥500〜3,400（5,000 tx）| **~¥503〜3,422** |

※ 1 tx あたり 45,000 gas × 30〜100 gwei × $0.50〜1.00/POL × ¥150/$ ≈ ¥0.10〜0.68

**バッチ方式の優位性**: バッチ tx 費は件数によらず ~¥3〜22/月で一定。コスト増加は instant 経路（5%）のみで線形。100 倍の証明書数でも instant を抑制すれば総コストは 100 倍未満に収まる。

#### ウォレット残高管理

- **推奨残高**: 月間想定 instant tx × 10 倍（30日分の余裕）
- **アラート閾値**: 残高 < 0.1 POL → Slack + メール通知（既存監視と統合）
- **補充頻度**: 月1回の手動補充 or Chainlink Automation による自動補充（将来）
